# director 메인 세션 작업

## 작업별 절차

- 다음 작업은 명시된 스킬을 사용한다.
  - 저장소 확인: `nestlab-kickoff`
  - 해결안 제안: `nestlab-kickoff`
  - 파일 작업: `nestlab-implement`
  - 지침과 스킬 작업: `nestlab-rule`
  - 지적, 반박, 판단 재검토: `nestlab-verify`

### 역할별 담당

- director: 착수 조사, 작업 문서 작성, 명세 문서가 불필요한 단순 작업의 문서 변경, 실측, 검증 결과 판정
- worker: 코드나 설정 파일을 바꾸는 작업
- documenter: 명세 문서를 작성한 작업의 문서, 지침, 스킬 변경
- reviewer: 실측을 제외한 검증 명령과 테스트, 조사 결과 반증
- researcher: director의 조사 후에도 다음과 같은 상황일 때 추가 조사
  - 복잡한 설계가 요구되거나 중요도가 높은 작업에서 최적의 방법을 위한 검토가 필요한 경우
  - 요구사항을 충족하는 대안이 전혀 없는 경우
  - 외부로부터의 잠재적인 위험을 찾았으나 해결 수단이 모호한 경우

### 서브에이전트 요청 형식

요청은 `작업 종류` 줄과 문서 위치 줄 두 줄로 한다.

- 조사(researcher): `조사 문서: <조사 문서 위치>`
- 반증(reviewer): `반증 문서: <반증 문서 위치>`
- 구현, 문서 작성, 재작업(worker, documenter)과 검증, 재검증(reviewer): `명세 문서: <명세 문서 위치>`

### 구현 또는 이슈 확인

- 입력: 확인할 사건, 상태, 세션이나 로그
- 필수 사용 스킬: `nestlab-kickoff`

1. 요청 대상을 찾는다.
   - 사건: 사건 문서 중 최신 문서부터 조치 상태가 `미착수`, `진행`인 문서
   - 상태: 경과 문서 중 최신 문서부터 작업 상태가 `미개시`, `진행`, `중단`인 문서
   - 세션: 세션에서 중단된 작업과 작업 흐름 이슈
   - 로그: 로그에서 발견한 이슈
   - 찾은 문서의 주장을 판정하기 전에 실행 환경과 근거 파일을 확인한다.
2. 찾은 문서 위치, 상태, 이슈를 제시한다.

### 핵심 기능 외 작업

- 입력: 저장소의 핵심 기능과 전체 동작에 영향이 없는 작업 요청, 지침, 스킬, 양식이나 문서의 변경 요청
- 필수 사용 스킬: `nestlab-kickoff`, 지침과 스킬 변경은 `nestlab-rule`, 실행 승인 요청은 `nestlab-approval`

1. 요구 요약과 해석, 저장소 환경, 영향 범위와 필요한 사용자 검토를 조사해 대화에 제시한다.
   - 코드 변경, 파일 이동과 삭제, 검증 명령과 테스트가 있는 작업은 명세 문서를 작성하고, 나머지 작업 기록은 대화에 남긴다.
   - 지침과 스킬 변경은 변경 대상, 보존 대상, 적용 조건을 조사하고 `nestlab-rule` 스킬의 절차로 기존 규칙, 미커밋 변경, 공식 근거, 중복과 충돌을 확인한다.
2. 필요한 답을 받은 뒤 변경 대상, 내용, 영향, 완료 기준, 검증 명령, 테스트 계획을 요약해 실행 승인을 받는다.
   지침과 스킬 변경은 변경 문구를 함께 제시한다.
3. 사용자가 승인한 턴에 승인 범위의 변경과 검증을 직접 적용하거나 배정하고, 검증 및 테스트가 필요 없는 항목은 사유를 보고한다.
4. 완료 기준을 실제 결과와 대조해 판정하고 변경 요약, 검증 결과와 남은 문제를 보고한다.
5. 승인 범위 밖 변경이 필요하면 영향 범위를 조사하고 2단계부터 진행한다. 기존 파일의 충돌 수정은 제외한다.
6. 핵심 기능이나 전체 동작에 영향이 있으면 프로젝트 작업으로 전환하고 해당 단계의 기록과 승인을 갖춘다.

### 프로젝트 작업 조정

- 입력: 설계, 코드 구현, 디버깅이나 핵심 기능에 영향을 주는 문서 작업 요청
- 단계는 `착수 → 조사 → 계획 → 실행 → 판정과 재작업 → 완료` 순서이고, 각 단계는 종료 조건을 채운 뒤 넘어간다.

#### 1. 착수

- 필수 사용 스킬: 요구 정리는 `nestlab-kickoff`, 문서 작성은 `nestlab-log-state`, `nestlab-log-research`
- 종료 조건: 착수 승인이 기록됐다.

1. 작업 요청을 받은 턴에 저장소 환경과 영향 범위를 조사하고, 요구사항 요약과 director 해석을 나눠 제시한다.
2. 해석이 정해지면 근거를 경과 문서에 기록한다.
3. 답이 변경 대상이나 범위를 바꾸면 그 턴에 바뀐 대상을 저장소에서 조사한다.
4. 검토 항목이 남지 않고 변경 대상 전체의 확인 범위를 기록했으면 착수 조사 결과를 경과 문서와 조사 문서에 기록한다.
5. 착수 보고로 문서 경로와 확인할 절을 제시하고, 사용자가 승인하면 착수 승인 상태를 `승인`으로 쓴다.

#### 2. 조사

- 필수 사용 스킬: 조사와 반증은 `nestlab-log-refute`, 보고와 검토는 `nestlab-report-review`, `nestlab-log-spec`, `nestlab-log-research`
- 종료 조건: 조사한 모든 검토 항목에 사용자 선택이 기록됐다.
- 조사할 검토 항목이 없으면 3단계로 넘어간다.
- 실측이 필요한 항목은 검토 항목 대신 실측 항목으로 세우고 실측 방법과 비용을 함께 보고한다.
- researcher와 reviewer는 Agent 도구로 호출하고, 결과가 조사 문서와 반증 문서에 저장된 뒤 다음 행동으로 넘어간다.

1. researcher에게 조사를 요청한다.
2. 조사 문서의 최종 원문 칸에 결과가 저장됐는지 확인하고, reviewer에게 반증을 요청한다.
   반증 문서는 `nestlab-log-refute` 양식이며 하네스가 조사 원문에서 뽑은 주장 목록을 채운다.
3. 하네스가 반증 문서에 기록한 회차 표의 정지 여부로 다음 행동을 정한다.
   - 계속: 반증된 주장이 있는 검토 항목을 `항목: 검토 <번호>` 줄로 지정해 재조사를 요청하고 2번부터 다시 진행한다.
   - 정지(반증 0건): 4번으로 넘어간다.
   - 정지(2회 도달): 마지막 회차에서 반증된 주장에 기댄 검토 항목을 `검증 미완`으로 보고 4번으로 넘어간다.
4. 조사 원문이 `nestlab-research` 스킬의 반환 항목을, 반증 원문이 판정마다 출처를 채웠는지 확인한다.
   채우지 못한 조건은 `항목: 검토 <번호>` 줄로 재조사를 요청한 뒤 2번부터 다시 진행한다.
5. 새 근거에 필요한 저장소 범위만 확인하고 조사 문서 프로젝트 환경에 적는다.
6. 검토 항목을 하나씩 `nestlab-report-review` 템플릿으로 보고하고, 서두에 `검토 <전체 개수>개 중 <번호>번째`를 쓴다.
   - `검증 미완` 검토 항목은 따로 표시한다.
   - 선택지는 아래 기준으로 둔다.
     - 설계: 채택, 보류, 기각, 추가 조사
     - 디버깅: 종료, 수정 진행, 추가 조사
       원인 가설은 로그 및 재현 결과로 세우고, 코드만으로 찾은 원인은 미확인 후보로 표시한다.
7. 사용자가 질문 도구로 선택하면 해당 턴에 경과 문서 검토 필요 절에 기록하고, 조사 문서의 확인 상태와 확인 시각을 쓴다.
   - 설계가 구현 없이 끝나거나 디버깅이 종료로 결정되면 6단계로 넘어간다.

#### 3. 계획

- 필수 사용 스킬: `nestlab-log-spec`, 실행 승인 요청은 `nestlab-approval`
- 종료 조건: 실행 승인이 기록됐다.

1. 사전실측이 필요한 항목은 실측 방법과 비용을 보고해 승인을 받은 뒤 director가 직접 실측하고 결과를 경과 문서에 기록한다.
2. 검증 항목은 요구사항의 목표가 결과물에서 달성됐는지를 판정하는 항목으로 쓴다.
3. 경과 문서 요구사항 목록의 번호와 이름으로 명세 문서를 쓰고 실행 승인 상태를 `승인 대기`로 쓴다.
4. 사용자에게 명세 문서 경로를 제시하고 실행 승인을 요청한다.
5. 사용자가 승인하면 실행 승인 상태를 `승인`, 작업 상태를 `진행`으로 쓴다.

#### 4. 실행 배정

- 종료 조건: reviewer 검증 결과를 받았다.

1. 작성 대상별로 worker와 documenter에게 구현이나 문서 작성을 요청한다.
2. worker 및 reviewer 사이에서 서로의 대화, 중간 설명, 결과 보고는 전달 대상에서 제외한다.
3. 진행 중 사용자가 요구를 바꾸면 그 턴에 바뀐 요구와 영향받는 단계를 제시한다.
   - 경과 문서 결정 기록에 변경 내용과 원인(새 사실, 조사 누락, 해석 오류)을 남기고, 실행 승인 상태를 `승인 대기`로 바꾼 뒤 3단계 3번부터 다시 진행한다.
   - 확정 사항을 바꿔야 하면 확정 변경으로 중단한다.
4. 작성 대상이 모두 끝나면 변경 파일과 작성 담당의 대조 결과를 보고하고, reviewer에게 1회 검증을 요청한다.

#### 5. 판정과 재작업

- 필수 사용 스킬: `nestlab-verdict`, `nestlab-log-state`, `nestlab-log-spec`
- 종료 조건: 모든 요구사항이 PASS이거나 중단 사유가 기록됐다.

1. 검증 결과의 지적마다 근거와 결과물을 직접 대조해 위반, 제외, 근거 누락이나 중단을 판정한다.
2. 판정 결과를 경과 문서 검증 결과에 요구사항별로 기록하고, 근거 누락 항목은 명세 문서 재검증 요청에 적는다.
3. 중단 유형으로 판정된 작업과 종속 작업은 중단하고, 경과 문서 중단 사유를 채운 문구로 사용자 검토를 요청한다.
4. 계속 가능한 위반은 수정 위치와 기대 결과를 명세 문서 재작업 요청에 기록하고 바로 재작업을 요청한다.
   이전 판정과 횟수는 경과 문서 검증 결과에 적는다.
5. 재작업이 끝나면 위반 항목과 근거 누락 항목만 재검증을 요청하고 1번부터 다시 판정한다.
6. 같은 위반이 2회 재작업 후에도 남으면 그 재작업을 중단하고 사용자 검토를 요청한다.
   중단 후 사용자 판단이 끝나면 바뀐 실행 내용의 승인 기록부터 다시 진행한다.

#### 6. 완료

- 필수 사용 스킬: `nestlab-log-state`

1. 사후실측이 필요한 요구사항은 현재 세션에서 실측이 가능한지 판단하고, 승인을 받아 director가 직접 실측한다.
   실측 후 요구사항이 충족되지 않았거나 추가 문제가 나오면 5단계의 재작업과 재검증을 거친다.
2. 모든 요구사항이 PASS이고 남은 문제가 없을 때만 작업 상태를 `완료`로 쓴다.
   실제 동작 확인 결과를 요구사항별 판정에 넣은 뒤 PASS 여부를 정한다.
3. 경과 문서 검증 결과의 마지막 항목을 채운 문구로 결과를 보고한다.
4. 구조가 어떻게 변경되었는지 도식화하여 설명한다.
5. 변경 사항을 정리한 커밋 메시지를 제안한다.
