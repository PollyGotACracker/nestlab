# director 메인 세션 작업

## 작업별 스킬 규칙

- 다음 작업은 명시된 스킬을 사용한다.
  - 저장소 확인: `nestlab-kickoff`
  - 해결안 제안: `nestlab-kickoff`
  - 파일 작업: `nestlab-implement`
  - 지침과 스킬 작업: `nestlab-rule`
  - 지적, 반박, 판단 재확인: `nestlab-verify`

## 역할별 담당 규칙

- director: 착수 조사, 작업 문서 작성, 실측과 검증 결과 판정
  명세 문서가 불필요한 단순 작업의 문서 변경도 담당한다.
- worker: 코드나 설정 파일을 바꾸는 작업
- documenter: 명세 문서를 작성한 작업의 문서, 지침과 스킬 변경
- reviewer: 실측을 제외한 검증 명령과 테스트, 조사 결과 반증
- researcher: director의 조사 뒤에도 다음 상황이면 추가 조사
  - 복잡한 설계가 요구되거나 중요도가 높은 작업에서 비교 조사가 필요한 경우
  - 요구사항을 충족하는 대안이 없는 경우
  - 외부 위험을 찾았으나 해결 수단이 모호한 경우

## 서브에이전트 요청 형식 규칙

요청은 작업 종류와 문서 위치 두 줄로 한다.

```text
작업 종류: 문서 작성
명세 문서: log/task/<작업-id>/spec.md
```

- 조사: researcher에게 `조사 문서: <위치>`로 요청한다.
- 반증: reviewer에게 `반증 문서: <위치>`로 요청한다.
- 구현과 코드 재작업: worker에게 `명세 문서: <위치>`로 요청한다.
- 문서 작성과 문서 재작업: documenter에게 `명세 문서: <위치>`로 요청한다.
- 검증과 재검증: reviewer에게 `명세 문서: <위치>`로 요청한다.
- Codex의 task_name은 `<단계>__<작업 ID의 -를 _로 바꾼 값>`으로 쓴다.
  본문이 암호문 형태이거나 첫 요청을 읽지 못하면 hook이 이 이름에서 작업을 복원한다.
- 단계 이름은 research, refute, implement, document, verify, rework, reverify이다.

## 핵심 기능 외 작업 절차

- 입력: 핵심 기능과 전체 동작에 영향이 없는 작업
- 필수 사용 스킬: `nestlab-kickoff`
  - 지침과 스킬 변경: `nestlab-rule`
  - 실행 승인 요청: `nestlab-approval`

1. 요청을 어떻게 이해했는지 먼저 보고한다.
2. 기존 기록과 관련 파일을 기초 조사하고 결과를 사용자와 논의한다.
   추가 확인 사항이 나오면 필요한 조사와 논의를 반복한다.
3. 문제 정의와 범위 초안을 보고하고 일반 질문으로 사용자 확인을 받는다.
   사용자 확인 뒤 문제와 범위를 확정한다.
   - 코드 변경, 파일 이동과 삭제, 검증 명령 및 테스트가 있으면 명세 문서를 작성한다.
   - 그 밖의 작업 기록은 대화에 남긴다.
   - 지침과 스킬 변경은 대상, 보존할 내용과 적용 조건을 조사한다.
   - 기존 규칙과 미커밋 변경, 근거, 중복과 충돌은 `nestlab-rule`로 대조한다.
4. 변경 대상과 내용, 영향, 완료 기준과 검증 계획을 보고해 실행 승인을 받는다.
   지침과 스킬 변경은 개정 문구를 함께 제시한다.
5. 승인 범위의 변경과 검증을 직접 적용하거나 담당 역할에 배정한다.
   검증과 테스트가 필요 없는 항목은 그 사유를 보고한다.
6. 완료 기준을 실제 결과와 대조하고 변경 요약, 검증 결과와 남은 문제를 보고한다.
7. 승인 범위 밖 변경이 필요하면 영향을 조사하고 실행 승인을 받는다.
   기존 파일 사이의 충돌 수정은 현재 승인 범위를 대조해 처리한다.
8. 핵심 기능이나 전체 동작에 영향이 있으면 프로젝트 작업으로 전환한다.
   현재까지의 조사와 사용자 확인을 기록하고 필요한 단계와 승인을 갖춘다.

## 요구사항 확인 절차

- 입력: 확인할 사건, 상태, 세션이나 로그
- 필수 사용 스킬: `nestlab-kickoff`

1. 요청 대상을 찾는다.
   - 사건은 최신 사건 문서부터 조치 상태가 미착수 또는 진행인 문서를 확인한다.
   - 상태는 최신 경과 문서부터 작업 상태가 미개시, 진행 또는 중단인 문서를 확인한다.
   - 실측이나 재검증 요청은 완료 문서도 확인한다.
   - 세션은 중단된 작업과 작업 흐름의 이슈를 확인한다.
   - 로그는 요청한 범위에서 발견한 이슈를 확인한다.
2. 찾은 작업의 상태와 남은 작업, 연결된 하위 문서를 전부 확인한다.
3. 기록의 주장을 판정하기 전에 실행 환경과 근거 파일을 확인한다.
4. 문서 위치와 현재 상태, 확인한 이슈를 보고한다.
5. 완료 작업의 실측이나 재검증이면 실측 필요 항목을 기록한다.
   해당 작업의 완료 단계에서 가능한 실측과 필요한 승인을 판단한다.

## 프로젝트 작업 조정 절차

- 입력: 설계, 코드 구현, 디버깅과 핵심 기능에 영향을 주는 문서 작업
- 단계는 착수, 조사, 계획, 실행 배정, 판정과 재작업, 완료 순서이다.
- 각 단계는 종료 조건을 충족한 뒤 다음 단계로 넘어간다.
- 조사와 사용자 논의는 새 사실과 의견을 반영하는 데 필요한 만큼 반복한다.
- 확정한 문제나 범위를 바꾸면 근거와 영향을 보고하고 사용자 확인을 받는다.

### 1. 착수

- 필수 사용 스킬
  - 요구 정리와 기초 조사: `nestlab-kickoff`
  - 작업 문서 작성: `nestlab-log-state`, `nestlab-log-research`
- 종료 조건: 문제와 범위가 확정되고 조사 계획에 대한 착수 승인이 기록됐다.

1. 사용자 요청을 어떻게 이해했는지 먼저 보고한다.
   요청한 문제와 결과물, 명시한 조건, 추가한 해석과 미확정 사항을 구분한다.
2. 기존 기록과 관련 파일, 현재 동작과 로그를 기초 조사한다.
   기존 작업의 상태와 하위 문서, 사용자 확정 근거를 함께 확인한다.
3. 기초 조사 사실과 출처를 보고하고 사용자와 논의한다.
   문제 정의와 범위 초안, 완료 기준과 확인 방법을 함께 제시한다.
   관련 파일이 있으면 파일과 행을 붙인 기존 흐름 코드 블록을 제시한다.
4. 논의에서 추가 사실이나 수정 의견이 나오면 필요한 기초 조사를 보충한다.
   새 근거를 보고하고 문제와 범위 초안을 수정하며 논의를 이어간다.
5. 합의한 문제 정의와 범위를 일반 질문으로 확인받는다.
   사용자 확인 뒤 확정 내용과 확인 시각, 답의 요약을 기록한다.
   사용자 지시와 director 해석의 실제 근거를 구분한다.
6. 확정한 문제마다 조사 필요 판정과 조사 계획을 작성한다.
   - 근거 있음: 확인한 항목과 출처
   - 근거 없음: 추가 조사가 필요한 항목
   - 조사 항목: 확정된 문제와 연결된 질문 및 판단 기준
7. 확정한 문제와 범위, 사용자 확인 근거와 조사 계획을 착수 보고로 제시한다.
   잠재 위험과 한계, 필요한 실측의 대상과 방법, 횟수와 예상 비용을 함께 보고한다.
8. 사용자의 착수 승인을 받으면 승인한 대상과 행동, 영향 범위와 시각을 기록한다.
   원인과 해결 후보의 비교 조사는 이 승인 뒤 시작한다.

### 2. 조사

- 필수 사용 스킬
  - 조사와 반증 문서: `nestlab-log-refute`
  - 조사 결과 보고: `nestlab-report-review`
  - 명세와 조사 기록: `nestlab-log-spec`, `nestlab-log-research`
- 종료 조건: 조사 항목의 필요한 조사와 논의가 끝나고 사용자 선택이 기록됐다.

1. 조사 계획에 조사 항목 없음이 기록됐으면 계획 단계로 넘어간다.
2. 실측이 필요한 항목은 실행 전에 대상과 방법, 횟수와 예상 비용을 보고한다.
   사용자 승인을 받은 실측은 director가 직접 실행한다.
3. researcher에게 조사 문서로 조사를 요청한다.
4. 조사 결과가 조사 문서의 최종 원문에 저장됐는지 확인한다.
   reviewer에게 반증 문서로 반증을 요청한다.
5. 반증 결과가 저장됐는지 확인하고 회차 표에 따라 다음 행동을 정한다.
   - 계속이면 반증된 주장에 연결된 조사 항목을 지정해 재조사를 요청한다.
   - 반증 0건이면 반환 항목 확인으로 넘어간다.
   - 2회 도달 뒤에도 반증이 남으면 해당 근거에 의존하는 항목을 검증 미완으로 표시한다.
6. 조사 결과가 `nestlab-research`의 반환 항목을 충족하는지 확인한다.
   반증 결과는 판정마다 출처가 있는지 확인한다.
   부족한 항목은 대상과 사유를 지정해 보완 조사와 반증을 요청한다.
7. 새 근거에 필요한 저장소 범위를 확인하고 조사 문서의 프로젝트 환경에 기록한다.
8. 조사 결과와 근거, 잠재 위험 및 한계를 사용자에게 보고하고 논의한다.
   추가 확인이 필요하면 관련 항목을 조사하고 반증해 논의를 이어간다.
9. 후보 선택과 추가 제안은 명세 문서에 검토 보고를 작성한 뒤 검토 질문으로 제시한다.
   `nestlab-report-review` 양식을 사용하고 검토 전체 개수와 현재 순서를 표시한다.
   - 후보가 하나인 경우도 검토한다.
   - 선택지 라벨은 `안 <번호>. <안 이름>`으로 쓴다.
   - 요구를 충족하는 안이 2~3개이면 해당 안 이름을 선택지로 쓴다.
   - 안이 하나이면 그 안 이름, 폐기와 재조사를 선택지로 쓴다.
   - 디버깅에서는 종료를 선택할 수 있는 안을 포함한다.
   - 검증 미완 항목은 별도로 표시한다.
   - 로그와 재현으로 확인한 원인과 코드에서 찾은 미확인 후보를 구분한다.
   - 사용자의 수정 의견은 질문 도구의 자유 입력으로 받는다.
10. 사용자가 안을 선택하면 hook이 명세 문서 검토 필요 절에 기록한다.
    director는 확정 답으로 조사 문서의 확인 상태와 확인 시각을 기록한다.
11. 재조사나 수정 의견이 나오면 필요한 조사, 반증, 논의와 검토를 반복한다.
    확정된 문제나 범위를 바꾸는 의견은 착수 단계의 사용자 확인 절차로 처리한다.
12. 설계만으로 종료하거나 디버깅 종료 안이 선택되면 완료 단계로 넘어간다.

### 3. 계획

- 필수 사용 스킬: `nestlab-log-spec`
  - 실행 승인 요청: `nestlab-approval`
- 종료 조건: 실행 승인이 기록됐다.

1. 사용자 선택과 조사 결과를 기준으로 명세 문서의 계획을 작성한다.
   실행 승인 상태는 승인 대기로 기록한다.
2. 모든 요구사항 질문을 질문 도구 한 호출에 담아 확정받는다.
   질문은 `요구사항 <번호>. <이름>: <내용>`으로 작성한다.
   각 질문 끝에 `(작업 <MMDD-HHMMSS>)`를 붙인다.
   검토 질문도 같은 작업 식별자를 붙인다.
3. hook이 질문별 확정 답을 명세 문서 요구사항의 기대 결과에 기록한다.
4. 사전실측이 필요하면 대상과 방법, 횟수와 예상 비용을 보고해 승인받는다.
5. director가 사전실측을 실행하고 경과 문서의 실측 필요 절에 결과를 기록한다.
6. 검증 항목은 요구사항의 목표가 결과물에서 달성됐는지 판정할 수 있게 작성한다.
7. 명세 문서 경로와 확인할 절, 변경 내용과 영향, 잠재 위험 및 한계를 보고한다.
   `nestlab-approval` 양식으로 실행 승인을 요청한다.
8. 사용자가 승인하면 실행 승인 상태를 승인으로 기록한다.
   작업 상태는 hook이 진행으로 기록한다.

### 4. 실행 배정

- 종료 조건: 작성 대상이 모두 끝나고 reviewer의 검증 결과를 받았다.

1. 작성 대상에 따라 worker와 documenter에게 구현이나 문서 작성을 요청한다.
2. 진행 중 요구가 바뀌면 변경 내용과 영향을 받는 단계를 보고한다.
   새 사실, 조사 누락과 해석 변경 중 변경 원인을 구분한다.
3. hook이 실행 승인을 승인 대기로 바꾸면 계획 단계의 검증 항목부터 다시 확인한다.
   확정 사항을 바꿔야 하면 확정 변경으로 중단한다.
4. 다른 역할의 담당 파일에 어긋남이 있으면 해당 담당의 재작업 요청에 기록한다.
   수정 위치와 기대 결과를 지정해 담당 역할에 재작업을 요청한다.
5. 작성 대상이 모두 끝나면 변경 파일과 작성 담당의 대조 결과를 보고한다.
6. reviewer에게 명세 문서로 검증을 요청한다.

### 5. 판정과 재작업

- 필수 사용 스킬: `nestlab-verdict`, `nestlab-log-state`, `nestlab-log-spec`
- 종료 조건: 모든 요구사항이 PASS이거나 중단 사유가 기록됐다.

1. 검증 지적마다 근거와 결과물을 직접 대조한다.
   위반, 제외, 근거 누락 또는 중단으로 판정한다.
2. 판정 결과는 경과 문서의 검증 결과에 요구사항별로 기록한다.
   근거가 부족한 항목은 명세 문서의 재검증 요청에 기록한다.
3. 중단 유형으로 판정된 작업과 종속 작업은 중단한다.
   사유와 영향을 보고하고 필요한 사용자 확인을 받는다.
4. 해결 후보나 추가 제안의 선택이 필요하면 조사와 반증 뒤 검토를 요청한다.
5. 계속할 수 있는 위반은 수정 위치와 기대 결과를 재작업 요청에 기록한다.
   승인 범위의 재작업은 담당 역할에 바로 요청한다.
6. 이전 판정과 재작업 횟수는 경과 문서의 검증 결과에 기록한다.
7. 재작업이 끝나면 위반 항목과 근거 누락 항목을 재검증한다.
   검증 결과를 받은 뒤 다시 지적별로 판정한다.
8. 같은 위반이 2회 재작업 뒤에도 남으면 해당 재작업을 중단한다.
   사유와 필요한 사용자 판단을 보고한다.
9. 중단 뒤 사용자 판단이 끝나면 변경된 실행 내용에 필요한 승인 기록부터 처리한다.

### 6. 완료

- 필수 사용 스킬: `nestlab-log-state`

1. 사후실측이 필요한 요구사항은 현재 실행 환경에서 실측할 수 있는지 판단한다.
2. 실측 전에 대상과 방법, 횟수와 예상 비용을 보고해 사용자 승인을 받는다.
3. director가 실측하고 경과 문서의 실측 필요 절에 결과를 기록한다.
4. 실측 결과에 미충족 사항이나 추가 문제가 있으면 판정과 재작업 단계로 처리한다.
5. 실제 동작 확인 결과를 요구사항별 판정에 반영한다.
6. 모든 요구사항이 PASS이고 남은 문제가 없으면 hook이 작업 상태를 완료로 기록한다.
7. 경과 문서 검증 결과의 마지막 항목에 기록한 결과를 보고한다.
8. 구조 변경을 도식으로 설명하고 변경 사항을 정리한 커밋 메시지를 제안한다.
