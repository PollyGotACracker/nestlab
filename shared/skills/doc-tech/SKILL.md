# 기술 지식 기록

## 인수

- `대상`: 기록할 기술과 사용자가 제공한 사실
- `결과`: 기술 지식 문서를 만들 파일 위치 또는 대화 초안

## 절차

1. 기술과 범위를 확인한다.
   - 대상 기술, 버전, 기록 목적을 요청에서 확인한다.
   - 결과에 영향을 주는 정보가 빠지면 필요한 이유와 함께 질문한다.
2. 외부 사실을 대상 버전의 공식 자료로 확인한다.
   - 공식 문서, 릴리스 노트, 이슈 트래커를 먼저 보고 블로그는 보조로만 쓴다.
   - 확인하지 못한 항목은 "확인 필요"로 표시한다.
3. 템플릿 항목을 모두 채운다.
   - 자료로 채울 수 없는 항목은 사유와 함께 "확인 필요"로 둔다.
   - 확인한 외부 사실에는 출처 링크를 단다.
4. `결과` 위치에 쓰고 기록 위치와 내용을 반환한다.
   - 기존 파일이 있으면 본문을 보존하고 바뀌는 부분을 먼저 보여준다.

## 템플릿

```markdown
# <기술 이름> <버전>

## 특징

- <핵심 특성>

## 개념

- <이해에 필요한 개념과 용어>

## 다른 기술과의 비교

| 기준   | <이 기술> | <비교 기술> |
| ------ | --------- | ----------- |
| <기준> | <값>      | <값>        |

## 주요 API

- `<이름>`: <용도와 시그니처>

## 제약과 이슈

- <제약, 알려진 이슈, 해결된 버전>

## 참고 자료

- [<자료 이름>](URL)
```

## 작성 기준

- 각 항목은 대상 버전에서 확인한 사실만 쓴다.
- 비교 항목은 같은 기준으로 대상별 값을 나란히 적는다.
- 개념 설명은 문서 이해에 필요한 최소 분량으로 쓴다.
- 구현 과정은 doc-design으로, 겪은 문제는 doc-troubleshooting으로 옮긴다.

## 결과물 예시

e.g. 가상 라이브러리 "fastq"의 기술 지식 문서

- 라이브러리, 버전, API, 링크는 예시용 가정이다.
- 실제 문서는 대상 버전의 공식 자료로 채운다.

```markdown
# fastq 2.1

## 특징

- 파이썬 비동기 작업 큐 라이브러리
- 작업 결과를 Redis에 저장한다.

## 개념

- 작업(job): 큐에 넣는 호출 하나
- 워커(worker): 큐에서 작업을 꺼내 실행하는 프로세스

## 다른 기술과의 비교

| 기준        | fastq     | Celery             |
| ----------- | --------- | ------------------ |
| 브로커      | Redis     | Redis, RabbitMQ 등 |
| 설정량      | 적음      | 많음               |
| 스케줄 기능 | 확인 필요 | 내장               |

## 주요 API

- `fastq.enqueue(func, *args)`: 작업을 큐에 넣고 작업 ID 반환
- `fastq.Worker(queue).run()`: 워커 시작

## 제약과 이슈

- 작업 결과 보관 기간 기본값은 24시간이다.
- 2.0의 결과 직렬화 오류는 2.1에서 수정됐다.

## 참고 자료

- [fastq 공식 문서](https://example.com/fastq/docs)
- [fastq 2.1 릴리스 노트](https://example.com/fastq/releases/2.1)
```
