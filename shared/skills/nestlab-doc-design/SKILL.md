## 공통 규칙

- 설계 문서 작성 시 기존 저장소 파일은 읽기만 허용한다.

## 작성 절차

### 1. 사실 수집

1. 기록할 사실을 수집한다.
   - 작업한 세션에서 호출하면 현재 세션의 대화, 도구 실행 결과, 변경 파일을 읽는다.
     읽은 기록에서 대상 기능의 범위, 요구사항, 채택한 방식, 고려했다 폐기 대안, 제약 조건, 구현 이유, 환경, 시도한 작업을 추출한다.
   - 다른 세션에서 한 작업이면 실행 중인 런타임의 세션 기록 파일을 작업 ID, 변경 파일 경로나 핵심 용어로 검색해 찾은 세션을 시작 시각 순으로 읽는다.
     - 세션 기록 위치는 그 런타임의 공식 문서에서 확인하고, 공식 문서에 없으면 런타임 홈 폴더(`CODEX_HOME` 등) 아래에서 대화 기록 파일을 찾는다.
     - 압축된 기록 파일은 풀어서 검색한다.
     - 기록 파일이 어느 저장소의 세션인지는 파일 안의 작업 디렉터리 값으로 확인한다.
   - 기록 파일이 지워진 세션은 그 사실을 보고하고, 같은 작업의 기록 문서와 `git log`로 보충한다.

### 2. 코드 조사

- 대상 기능과 관련된 코드만 읽고, 레포 전체 탐색은 생략한다.
- 읽을 범위에서 node_modules, vendor, dist, build, .venv, 락 파일을 뺀다.
- 읽을 대상은 다음과 같다.
  - 해당 기능의 진입점과 호출 경로
  - 인터페이스 정의(함수 시그니처, 타입, 스키마, 엔드포인트)
  - 이 기능이 의존하는 외부 라이브러리와 그 버전
  - 관련 설정값과 환경변수
  - `git log --oneline -- <경로>` 실행 결과
- 로그 출력이 200줄을 넘으면 경로, 기간, 검색어로 범위를 좁혀 다시 실행한다.
- 코드로 직접 드러나지 않는 내용은 가능한 git 명령어를 사용하여 확인한다.
  - 구현 목적, 발생한 문제, 설계 과정, 최종 설계 채택 근거 등

### 3. 웹 검색

- 웹 검색은 아래 범위로 한정한다.
  - 사용 중인 라이브러리와 프레임워크의 권장 패턴과 그 근거: `구조` 또는 `설계 흐름`에 반영
  - 관련 라이브러리의 기본 동작, 기본값, 버전별 변경: 해당 내용이 나오는 절에 반영
  - 이 문제 영역의 알려진 접근법과 각각의 트레이드오프: `설계 흐름`의 비교 근거로만 반영
  - 설계 이해에 필요한 중요 개념 설명: 개념이 처음 나오는 절에 한두 문장으로 반영
  - 커맨드와 설정 항목 설명: 해당 항목 바로 아래에 반영
- 검색 전에 의존성 파일에서 라이브러리의 실제 버전을 확인하고 그 버전의 문서를 먼저 본다.
- 공식 문서, 릴리스 노트, 이슈 트래커를 먼저 보고 블로그는 보조로만 쓴다.
- 검색으로 가져온 문장에는 그 자리에 출처 링크를 단다.
- 개념 설명은 문서 이해에 필요한 최소 분량으로 쓴다.

### 4. 문서 작성

#### 내용

- `코드 참조`, `Git 참조`, `참고 자료`, `메모` 절을 제외한 문서의 길이는 공백 제외 최소 3000자 이상으로 한다.
- 사용자가 언급한 내용과 저장소에서 확인한 내용만 쓴다.
- 문맥을 고려했을 때 필요하지만 자료가 없어 내용을 작성할 수 없는 자리에는 해당 위치에 다음과 같이 둔다.
  `<!-- TODO: 무엇이 불명확한지 -->`
- `구현 이유`, `환경`, `필요 조건과 기술`은 사용자 진술이나 실행 결과로 확인한 것만 작성한다.
- `설계 흐름` 내부 절은 아래 내용을 각 문단으로 작성한다.
  - 최종 채택의 구조와 채택 근거  
    (확인된 구조나 코드의 코드 블록 1개 이상을 포함하여 최소 1500자 이상 작성)
  - 폐기한 대안과 폐기 근거
  - 알려진 제약 또는 한계
- 웹 검색으로 찾은 일반적인 대안은 `설계 흐름` 본문에서 비교 근거로 언급하고 출처를 `참고 자료` 절에 추가한다.
- `코드 참조`에는 실제로 확인한 파일을 저장소 루트 기준 상대경로로 적는다.
- `참고 자료`에는 실제로 열람한 자료를 링크로 적는다.
- 과정이 드러나는 내용만 순서대로 쓰고, 나머지는 중요도 순으로 쓴다.

#### 소제목

- `설계 흐름` 안의 소제목은 선택 하나당 하나씩 둔다.
- `구조`와 `데이터 흐름` 안의 소제목은 아래 조건을 전부 만족할 때 쓴다.
  - 그 절이 4문단을 넘는다.
  - 독립적으로 다룰 주제가 2개 이상이다.
- 소제목은 평서형 명사구로 쓴다.
- 소제목만 읽어도 무엇을 시도했고, 선택했는지 알 수 있어야 한다.
- `설계 흐름` 안의 소제목은 실제 선택되어 구현된 내용을 명시한다.
  e.g. 좋음: `재시도 간격 고정`
  e.g. 나쁨: `재시도 정책 선택`, `왜 고정 간격인가`, `설계 고려사항`
- `구조` 안의 소제목은 구성 요소나 계층의 이름을 명시한다.
  e.g. 좋음: `요청 라우팅 계층`
  e.g. 나쁨: `전체 구조 개요`, `아키텍처는 어떻게 되는가`

#### 서술

- 각 절은 결론부터 쓰고, 배경 설명은 뒤에 둔다.
- 한 문단은 3~5문장이고 한 가지만 다룬다.
- 같은 주제의 세부 요소 여러 개는 목록으로 쓴다.
- 같은 내용은 한 번만 쓴다.
- 절은 마지막 사실에서 끝낸다.
- 저장소 작업자 관점에서 작성하되 1인칭 표현("나는", "저는")은 제거한다.
- 폴더 구조, 코드 등 저장소에서 찾은 내용물은 다음과 같이 작성한다.
  - 변수명, 경로명 등에서 개인 설정이나 정보, 저장소 도메인이 특정되는 명칭이 없어야 한다.
  - 설명하려는 내용에서 벗어나거나, 동작에 불필요한 코드는 제거한다.
  - 코드 블록 내에 둔다.
- 문서에 참조를 위한 별도 기호를 제거한다.

### 5. 승인과 저장

1. 최종 결과물을 적용된 지침 및 스킬과 대조한 후, 어긋난 내용을 수정한다.
2. 생성할 문서 전문과 기존 승인 범위를 대조하고 새 승인이 필요한 변경은 사용자 확인을 받는다.
   1. frontmatter 값을 얻는 아래 커맨드를 실행한다.
      - repo: `basename $(git rev-parse --show-toplevel)`
      - updated: `date +%F`
   2. 커맨드 출력을 그대로 frontmatter 값으로 쓴다.
3. markdown 파일을 생성한다.  
   별도 지시가 없다면 파일명은 해당 주제의 한국어로 공백은 유지하며, 파일 경로는 세션 경로 루트에 둔다.  
   여러 주제를 작성하는 경우 각 파일로 분리한다.
4. 승인 범위 안에서 결과 위치에 파일을 쓰고 경로를 출력한다.
