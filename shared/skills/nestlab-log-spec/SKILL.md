# 명세 문서

## 작성 시점 규칙

- 조사 단계에서 검토 안을 작성하기 전에 초안을 만들고, 계획 단계에서 요구사항을 채운다.
- 승인, 재작업 요청, 재검증 요청은 해당 사건이 생길 때 갱신한다.

## 작성 규칙

- 문서 위치는 프로젝트 전역 지침 경로 목록의 명세 문서이다.
- 서브에이전트가 이 문서만 읽고 작업하므로 요구사항, 변경 범위, 검증 기준을 이 문서 안에서 완결한다.
- 요구사항 절의 기대 결과 칸은 hook이 확정된 요구사항 문장으로 쓴다.
- 검토 필요에는 조사 이후 후보 선택과 추가 제안을 기록한다. 후보가 하나인 경우도 포함한다.
- 검토 필요는 hook이 검토 질문의 선택지 답으로 같은 번호를 바꾸고, 없는 번호를 덧붙인다.
  직접 입력과 재조사 답은 기록 대상에서 제외한다.
- `검토 <번호>.` 질문 전에 검토 보고 절을 먼저 쓴다.
  `#### 검토 <번호>. <이름>` 아래에 비교표와 안 블록을 두고, 비교표 행은 질문의 선택지 라벨과 같게 쓴다.
- 안 블록은 검토 하나에 3개 이하로 쓴다.
- 안 블록마다 `장점` 줄과 `단점` 줄을 쓰고, 줄마다 출처 괄호(`파일:행` 또는 URL)를 붙인다.
  hook이 두 줄이나 출처 괄호가 없는 안 블록의 쓰기를 거부한다.
- 안 블록의 적용할 작업마다 사용자 지시 로그 시각이나 `파일:행`을 붙이고, 없으면 `[해석]`을 붙인다.

- 문서 갱신 대상 칸에는 착수 조사가 반환한 문서 갱신 대상을 적는다.
- 재작업 요청과 재검증 요청에는 처리 대기 항목만 둔다.
- 요구사항과 재작업의 기대 결과에는 수정 후 결과물에서 관측할 동작을 쓴다.
- 검증 명령, 실행 담당과 관측 방법은 검증 계획과 재검증 요청에 쓴다.
- 작성 담당은 기대 동작에 맞는 결과물과 테스트 코드를 작성하고, 검증 담당은 명령을 실행한다.
- 검증 항목은 아래 기준으로 세운다.
  - 요구사항마다 1개 이상 둔다.
  - 항목마다 원문을 대조하는 정적 확인과 실제 경로와 입력으로 실행하는 실제 동작 확인을 구분한다.
  - 측정할 수 없는 항목은 `미측정`과 대안을 적는다.
  - 차단 규칙을 바꾼 작업은 규칙마다 차단 사례와 지침을 지킨 입력의 허용 사례를 1개 이상 둔다.
  - 테스트 기대값은 지침, 스킬 양식, 명세 문서의 기대 결과에서 가져온다.
    hook 테스트의 작업 문서 입력은 해당 스킬 `Template` 절 양식으로 만든다.
    사유 문구는 지침이나 명세 문서가 정한 문구만 검사하고, 그 밖에는 판정 결과만 검사한다.
- Test Case 종류는 다음과 같다.
  - 차단: 규칙이나 기능이 반응해야 하는 입력
  - 허용: 지침을 지켜 반응하지 않아야 하는 입력
- Test Case 요구사항마다 차단 행과 허용 행을 하나 이상 둔다.
- Test Case 명령은 검증 담당이 그 입력을 시험할 명령이고, 기대 결과는 입력에 대한 관측값이다.
- 사용자 메시지는 핵심만을 요약한다.
- 실제 검증의 확인 수단 출처에는 그 수단을 고른 근거를 적는다.
  사용자 확인을 수단으로 쓰면 에이전트 도구로 시도한 경로와 그 결과를 적는다.
- 시각 형식: `<YYYY-MM-DD HH:MM:SS>`

### 사용 커맨드

- 시각(KST): `TZ=KST-9 date '+%Y-%m-%d %H:%M:%S'`
- 기준 커밋: `git log -1 --format=%h`
