## 공통 규칙

- 트러블슈팅 문서 작성 시 기존 저장소 파일은 읽기만 허용한다.

## 작성 절차

### 1. 사실 수집

1. 기록할 사실을 수집한다.
   - 작업한 세션에서 호출하면 현재 세션의 대화, 도구 실행 결과, 변경 파일을 읽는다.
     읽은 기록에서 실행 환경, 증상(의도한 동작과 실제 동작), 발생 조건, 원인, 원인 확정 여부, 시도했다 버린 방법을 추출한다.
   - 다른 세션에서 한 작업이면 실행 중인 런타임의 세션 기록 파일을 작업 ID, 변경 파일 경로나 핵심 용어로 검색해 찾은 세션을 시작 시각 순으로 읽는다.
     - 세션 기록 위치는 그 런타임의 공식 문서에서 확인하고, 공식 문서에 없으면 런타임 홈 폴더(`CODEX_HOME` 등) 아래에서 대화 기록 파일을 찾는다.
     - 압축된 기록 파일은 풀어서 검색한다.
     - 기록 파일이 어느 저장소의 세션인지는 파일 안의 작업 디렉터리 값으로 확인한다.
   - 기록 파일이 지워진 세션은 그 사실을 보고하고, 같은 작업의 기록 문서와 `git log`로 보충한다.

### 2. 코드 조사

- 주제와 관련된 코드만 읽고, 레포 전체 탐색은 생략한다.
- 읽을 범위에서 node_modules, vendor, dist, build, .venv, 락 파일을 뺀다.
- 읽을 대상은 다음과 같다.
  - 해당 기능의 진입점과 호출 경로
  - 인터페이스 정의(함수 시그니처, 타입, 스키마, 엔드포인트)
  - 이 기능이 의존하는 외부 라이브러리와 그 버전
  - 관련 설정값과 환경변수
  - `git log --oneline -- <경로>` 실행 결과
- 로그 출력이 200줄을 넘으면 경로, 기간, 검색어로 범위를 좁혀 다시 실행한다.
- 코드로 직접 드러나지 않는 내용은 가능한 git 명령어를 사용하여 확인한다.
  - 구현 목적, 발생한 문제, 설계 과정, 최종 설계 선택 이유 등

### 3. 웹 검색

- 웹 검색은 아래 범위로 한정한다.
  - 에러 메시지와 예외 이름의 의미, 그것이 나타내는 상태: `## 증상`에 반영
  - 관련 라이브러리의 기본 동작, 기본값, 버전별 변경: `## 원인`에 반영
  - 공식 문서의 권장 대응, 알려진 이슈의 픽스 버전: `## 해결`에 반영
  - 에러 또는 해결에 관련된 중요 개념 설명: 개념이 처음 나오는 절에 한두 문장으로 반영
  - 커맨드와 설정 항목 설명: 해당 항목 바로 아래에 반영
- 개념 설명은 문서 이해에 필요한 최소 분량으로 쓴다.
- 검색 전에 의존성 파일에서 라이브러리의 실제 버전을 확인하고 그 버전의 문서를 먼저 본다.
- 공식 문서, 릴리스 노트, 이슈 트래커를 먼저 보고 블로그는 보조로만 쓴다.
- 검색으로 가져온 문장에는 그 자리에 출처 링크를 단다.

### 4. 문서 작성

#### 내용

- `코드 참조`, `Git 참조`, `참고 자료`, `메모` 절을 제외한 문서의 길이는 공백 제외 최소 1500자 이상으로 한다.
- 사용자가 언급한 내용과 저장소에서 확인한 내용만 쓴다.
- 문맥을 고려했을 때 필요하지만 내용을 작성하기 어려운 자리에는 다음과 같이 둔다. 그 외의 주석은 제거한다.  
  `<!-- TODO: 무엇이 불명확한지 -->`
- `증상`과 `원인`을 분리한다. 관측은 `증상`에, 해석은 `원인`에 쓴다.
- 이 레포 코드나 사용자 진술로 확인되지 않은 원인은 `## 원인`의 가설 목록에 쓴다.
  검색 결과에 흔한 원인이 나와도 같다.
  무엇을 확인해야 판정되는지 함께 적는다.
- `의도한 동작`, `실제 동작`, `실행 환경`도 사용자 진술이나 실행 결과로 확인한 것만 쓰고, 빈 자리에는 TODO 주석을 남긴다.
- `코드 참조`의 파일은 레포 루트 기준 상대경로로 적고, 코드에서 실제로 확인한 심볼만 적는다. 없으면 표를 비운다.
- `참고 자료`에는 실제로 열람한 자료만 링크로 적는다.
- 시간 순서가 의미 있는 내용(`조사 과정`, `시도 순서`)만 순서대로 쓰고, 나머지는 중요도 순으로 쓴다.

#### 소제목

- `## 원인`과 `## 해결` 안의 소제목은 아래 조건을 전부 만족할 때 쓴다.
  - 그 절이 4문단을 넘는다.
  - 독립적으로 다룰 주제가 2개 이상이다.
- 소제목은 평서형 명사구로 쓴다.
- 소제목만 읽어도 무슨 일이 있었는지 알 수 있어야 한다.
- `## 원인` 안의 소제목은 각 상세 원인을 명시한다.
  e.g. 좋음: `### 세션 반환 문제`  
  e.g. 나쁨: `### 근본 원인은 무엇인가`, `### 원인 분석`, `### 문제의 배경`
- `## 해결` 안의 소제목은 한 일을 명시한다.
  e.g. 좋음: `### 세션 범위 고정`  
  e.g. 나쁨: `### 해결 방법`, `### 어떻게 고쳤는가`, `### 접근 방식`

#### 서술

- 각 절은 결론부터 쓰고, 배경 설명은 뒤에 둔다.
- 한 문단은 3~5문장이고 한 가지만 다룬다.
- 같은 주제의 세부 요소 여러 개는 목록으로 쓴다.
- 같은 내용은 한 번만 쓴다.
- 절은 마지막 사실에서 끝낸다.
- 저장소 작업자 관점에서 작성하되 1인칭 표현("나는", "저는")은 제거한다.
- 폴더 구조, 코드 등 저장소에서 찾은 내용물은 다음과 같이 작성한다.
  - 변수명, 경로명 등에서 개인 설정이나 정보, 저장소 도메인이 특정되는 명칭이 없어야 한다.
  - 설명하려는 내용에서 벗어나거나, 동작에 불필요한 코드는 제거한다.
  - 코드 블록 내에 둔다.
- 문서에 참조를 위한 별도 기호를 제거한다.

### 5. 승인과 저장

1. 최종 결과물을 적용된 지침 및 스킬과 대조한 후, 어긋난 내용을 수정한다.
2. 생성할 문서 전문과 기존 승인 범위를 대조하고 새 승인이 필요한 변경은 사용자 확인을 받는다.
   1. frontmatter 값을 얻는 아래 커맨드를 실행한다.
      - repo: `basename $(git rev-parse --show-toplevel)`
      - updated: `date +%F`
   2. 커맨드 출력을 그대로 frontmatter 값으로 쓴다.
   3. status는 원인이 확정되고 해결이 적용됐으면 `resolved`, 그 밖에는 `open` 값 하나만 쓴다.
3. markdown 파일을 생성한다.  
   별도 지시가 없다면 파일명은 해당 주제의 한국어로 하며, 파일 경로는 세션 경로 루트에 둔다.  
   여러 주제를 작성하는 경우 각 파일로 분리한다.
4. 승인 범위 안에서 결과 위치에 파일을 쓰고 경로를 출력한다.

repo: repo-a
type: troubleshooting
updated: 2026-08-29
