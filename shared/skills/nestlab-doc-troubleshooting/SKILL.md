# 트러블슈팅 문서 작성

## 절차

1. 기록할 사실을 모은다.
   - 작업한 세션에서 호출하고, 현재 세션의 대화, 도구 실행 결과, 변경 파일에서 실행 환경, 증상(의도한 동작과 실제 동작), 발생 조건, 원인, 원인 확정 여부, 시도했다 버린 방법을 추출한다.
   - 다른 세션에서 한 작업이면 실행 중인 런타임의 세션 기록 파일을 작업 ID, 변경 파일 경로나 핵심 용어로 검색해 걸린 세션을 시작 시각 순으로 읽는다.
     - 세션 기록 위치는 그 런타임의 공식 문서에서 확인하고, 공식 문서에 없으면 런타임 홈 폴더(`CODEX_HOME` 등) 아래에서 대화 기록 파일을 찾는다.
     - 압축된 기록 파일은 풀어서 검색한다.
     - 기록 파일이 어느 저장소의 세션인지는 파일 안의 작업 디렉터리 값으로 확인한다.
   - 기록 파일이 지워진 세션은 그 사실을 보고하고, 같은 작업의 기록 문서와 `git log`로 보충한다.
   - 파일명과 결과 위치는 요청에서 확인한다.
     파일명은 확장자 없이 적고, 결과 위치가 폴더이고 없으면 만든다.
     현재 저장소 안의 파일은 요청이 그 위치를 지정할 때만 만들거나 수정한다.
2. 조사한다.
   - 주제와 관련된 코드만 읽고, 레포 전체 탐색은 생략한다.
   - node_modules, vendor, dist, build, .venv, 락 파일은 읽지 않고 건너뛴다.
   - 읽을 것
     - 해당 기능의 진입점과 호출 경로
     - 인터페이스 정의(함수 시그니처, 타입, 스키마, 엔드포인트)
     - 이 기능이 의존하는 외부 라이브러리와 그 버전
     - 관련 설정값과 환경변수
     - `git log --oneline -- <경로>` 실행 결과
   - 로그 출력이 200줄을 넘으면 경로, 기간, 검색어로 범위를 좁혀 다시 실행한다.
3. 웹 검색은 아래 범위로 한정한다.
   - 에러 메시지와 예외 이름의 의미, 그것이 나타내는 상태: `## 증상`에 반영
   - 관련 라이브러리의 기본 동작, 기본값, 버전별 변경: `## 원인`에 반영
   - 공식 문서의 권장 대응, 알려진 이슈의 픽스 버전: `## 해결`에 반영
   - 에러 또는 해결에 관련된 중요 개념 설명: 개념이 처음 나오는 절에 한두 문장으로 반영
   - 커맨드와 설정 항목 설명: 해당 항목 바로 아래에 반영
   - 개념 설명은 문서 이해에 필요한 최소 분량으로 쓰고, 튜토리얼 분량은 제외한다.
   - 검색 전에 의존성 파일에서 라이브러리의 실제 버전을 확인하고 그 버전의 문서를 먼저 본다.
   - 공식 문서, 릴리스 노트, 이슈 트래커를 먼저 보고 블로그는 보조로만 쓴다.
   - 검색으로 가져온 문장에는 그 자리에 출처 링크를 단다.
4. 조사 결과를 출력하고 멈춘다.
   - 읽은 파일 목록
   - 코드에서 확인한 구조: 구성 요소, 데이터 흐름, 외부 의존
   - 관례에서 벗어나 보이는 선택: 위치 `파일:줄`과 특이한 점을 적은 표
   - 사용자 입력에서 추출한 것: 항목별로 넣을 위치
   - 여전히 비는 항목: 없으면 "없음"
   - 비는 항목은 대부분 "왜 그렇게 했는가"와 "무엇을 고려했다 버렸는가"이다.
     이 내용은 코드에 남지 않는 내용이라 추측 대신 빈 항목으로 둔다.
5. 생성할 문서 전문을 조사 결과 뒤에 이어서 출력하고 승인을 받는다.
   - 승인 전에는 파일 생성을 보류한다.
6. 승인을 받으면 결과 위치에 파일을 쓰고 경로만 출력한다.
   - 요약이나 소감 없이 경로로 끝낸다.

## frontmatter 값

아래 명령을 실행하고 출력값을 그대로 쓴다. 기억이나 추측으로 채우는 값은 쓰지 말고 명령 출력만 쓴다.

- repo: `basename $(git rev-parse --show-toplevel)`
- updated: `date +%F`
- status: 원인이 확정되고 해결이 적용됐으면 `resolved`, 그 밖에는 `open`
  값 하나만 쓰고, 설명 문구는 제외한다.

## 규칙

- 파일을 쓰기 전에 파일 전체 내용을 사용자에게 보여주고 승인을 받는다.
- 파일이 이미 있으면 기존 본문을 보존한다.
  본문을 고쳐야 하면 바뀌는 부분과 방식을 사용자에게 먼저 보여주고 승인을 받는다.
- 사용자가 말한 것과 코드에서 확인한 것만 쓴다.
  빈 자리에는 `<!-- TODO: 무엇이 불명확한지 -->`를 남긴다.
- `증상`과 `원인`을 분리한다. 관측은 `증상`에, 해석은 `원인`에 쓴다.
- 검색 결과에 흔한 원인이 나와도 이 레포 코드나 사용자 진술로 확인되지 않았으면 `## 원인`에 단정으로 쓰지 말고 가설 목록에 넣는다.
  무엇을 확인해야 판정되는지 함께 적는다.
- `의도한 동작`, `실제 동작`, `실행 환경`도 사용자 진술이나 실행 결과로 확인한 것만 쓰고, 빈 자리에는 TODO 주석을 남긴다.
- `코드 참조`의 파일은 레포 루트 기준 상대경로로 적고, 절대경로는 쓰지 말고 코드에서 실제로 확인한 심볼만 적는다. 없으면 표를 비운다.
- `참고 자료`에는 실제로 열람한 자료만 링크로 적는다.
- `## 메모` 아래는 어떤 경우에도 수정하거나 삭제하지 말고 그대로 보존한다.
- 이모지와 평가 형용사는 쓰지 말고 사실만 적는다.

### 1. 소제목

- `## 원인`과 `## 해결` 안의 소제목(`###`)은 아래 조건을 전부 만족할 때 쓴다.
  - 그 절이 4문단을 넘는다.
  - 독립적으로 다룰 갈래가 2개 이상이다.
- 조건이 맞지 않으면 소제목 없이 문단으로만 쓴다. 내용이 짧으면 소제목으로 구조를 만들어내지 말고 문단으로 둔다.
- `## 원인` 안의 소제목은 각 상세 원인의 명사구로 쓴다.
  e.g. 좋음 `### 세션이 반환되지 않음`, 나쁨 `### 근본 원인은 무엇인가`, `### 원인 분석`, `### 문제의 배경`
- `## 해결` 안의 소제목은 한 일을 서술한 명사구로 쓴다.
  e.g. 좋음 `### 세션 범위 고정`, 나쁨 `### 해결 방법`, `### 어떻게 고쳤는가`, `### 접근 방식`
- 소제목은 평서형 명사구로 쓰고, `분석`, `배경`, `개요`, `정리`, `방법`, `접근`으로 끝나는 말은 다른 명사로 바꾼다.
- 소제목만 읽어도 무슨 일이 있었는지 알 수 있어야 한다.

### 2. 서술

- 각 절은 결론부터 쓰고, 배경 설명은 뒤에 둔다.
- 한 문단은 3~5문장이고 한 가지만 다룬다.
- 같은 주제의 세부 요소 여러 개는 목록으로 쓴다.
- 같은 내용을 표현만 바꿔 반복하지 말고 한 번만 쓴다.
- 절 끝에는 요약 문단을 붙이지 말고 마지막 사실에서 끝낸다.
- 시간 순서가 의미 있는 내용(조사 과정, 시도 순서)만 순서대로 쓰고, 나머지는 중요도 순으로 쓴다.
- 1인칭 표현("나는", "저는")은 빼고 사실만 쓴다.

# Redis 연결 풀 고갈로 발송 중단

## 실행 환경

- Ubuntu 24.04 컨테이너, Python 3.12, redis-py 5.0.1, Redis 7.2
- 실행 명령: `python -m notifier.worker`

## 증상

- 의도한 동작: 큐에 쌓인 알림을 계속 발송한다.
- 실제 동작: 가동 40분 뒤 `redis.exceptions.ConnectionError: Too many connections`가 반복되고 발송이 멈춘다.

## 재현

알림 1,000건을 연속으로 넣으면 40분 안에 재현된다. 알림 100건 이하에서는 미확인이다.

## 원인

처리기가 알림마다 새 클라이언트를 만들고 닫지 않아 연결 풀 한도(기본 `max_connections` 값)에 도달했다.

- 알림마다 `Redis()`를 생성한다. 근거는 코드 참조의 `Worker.send()`이다.
- 클라이언트를 닫는 호출이 없다. 근거는 같은 함수의 전체 본문이다.

## 해결

클라이언트를 모듈 수준에서 하나만 만들고 모든 알림이 공유하도록 바꿨다. 적용 뒤 2시간 가동에서 같은 에러가 없었다.

## 시도했다 버린 것

- `max_connections` 상향: 고갈 시점이 늦춰질 뿐 원인이 남아 있어 제외했다.

## 코드 참조

| 무엇      | 심볼            | 파일            |
| --------- | --------------- | --------------- |
| 알림 발송 | `Worker.send()` | `src/worker.py` |
