## 공통 규칙

- Markdown에서만 유효한 규칙 항목은 .md 파일에만 적용한다.

### 변경과 보존

- 사용자와 다른 작업자의 기존 변경은 승인된 수정 대상과 구분해 보존한다.
- 요청 내용, 구조, 방식과 결과물을 작업 범위로 정한다.
- 작업 범위 외의 수정은 작업 목표 및 내용와 연관된 경우의 다음 항목으로 한정하며, 해당 턴에서 수정한다.  
  모든 작업 범위 외 수정은 보고 응답에 수정 전후 내용과 근거를 포함해야 한다.
  - 기존 문서에서 현재 작업 내용과 충돌하는 내용을 발견하면 현재 작업 기준으로 수정한다.
  - 이번 변경과 충돌하는 경로 또는 문서 참조가 있다면 수정한다.
  - 각 지시 문장을 봤을 때 요구되는 구체적인 행동을 파악하기 어렵다면 수정한다.
  - 각 절차 절을 봤을 때 행동을 개시해야 할 시점, 작업의 흐름이 명확하지 않다면 수정한다.
  - 본문 전체의 서식과 문서 구조가 일관적이지 않다면 수정한다.  
    기존에 작성된 서식이 아닌 작성된 내용을 서식 지침 적용 기준으로 둔다.

### 문장

- 근거 없는 수식어, 상투적 평가어, 당위적 강조를 제거한다.
- 문장마다 핵심 하나만 담는다.
- 목록과 주석은 완결된 문장마다 줄바꿈한다.
- 핵심 단어는 **굵게**, 강조할 단어는 *기울임*으로 표시한다.
  절 범위에서 한 번 이하로 사용한다.
- 세션의 사용자를 직접 가리키는 표현을 제거한다.
- 세션 대화나 현재 작업 맥락을 포함하는 내용을 제거한다.
- 프로젝트 구조와 경로에서 개인 폴더명은 임의 폴더명으로 대체한다.

### 정보 구조

- 별도 형식이 없으면 다음 기준을 적용한다.
  - 문단: 배경, 기술 원리, 설계 이유, 인과관계, 분석과 해석
  - 글머리 목록: 병렬 관계인 항목, 조건, 요구사항, 확인 사항
  - 번호 목록: 순서, 선행 의존성, 단계별 작업과 절차
  - 표: 여러 대상의 동일한 속성, 수치, 변경 전후 비교
  - 코드 블록: 코드, 명령어, 설정, 데이터 구조와 실행 예시
  - 그림: 구성 요소의 관계, 데이터 흐름, 상태 변화와 처리 과정
  - Heading: 독립적으로 설명할 주제나 내용의 구분
- 서식 지침과 기존 문서 서식의 충돌은 지시된 사항대로 적용한다.
- 사용자 요청으로 지정된 분류와 Heading을 우선하며, 지정이 없으면 원문의 주제에 따라 분류한다.
- 문서 전체에서 제목, 본문, 목록의 구조와 서식을 일관되게 작성한다.
- 기존 문서에서 사용하는 용어와 표현, 통용되는 용어를 사용하고, 같은 개념에는 같은 용어를 사용한다.
- 독자가 읽는 순서에 맞춰 내용을 배치하고, 앞뒤 문맥의 연결과 설명의 선후 관계를 확인한다.

### 목록과 제목

- 목록 사이의 빈 줄은 제거하고, 들여쓰기와 YAML 프론트매터는 공백 2개를 사용한다.
- 글머리 목록의 보충 설명은 항목 아래 들여쓴 무기호 3줄 이하로 작성할 수 있다.
- 주제가 둘 이상이면 `##` 이하의 Heading으로 구분하고, Heading은 4어절 이하의 명사구로 작성한다.

### 예시와 인용

- 예시와 참고 정보는 각각 `e.g.`, `cf.`로 표기하고 한 칸 띄운다.
- 예시는 대상을 명시하고, 내용이 길면 코드 블록으로 작성한다.
- 인물 발언은 인용 블록 마지막 줄에 `— 이름, 소속(직책)`을 붙인다.

### 코드와 시각 자료

- 커맨드, 프롬프트, 템플릿은 적절한 형식이 지정된 코드 블록으로 작성한다.
- 전체 흐름은 간단하면 코드 블록 안에 `→`, `↔`로 연결하고, 복잡하면 Mermaid를 사용한다.
- 폴더 구조는 tree 형식으로 작성한다. e.g. `├──`, `└──`, `│`
- 표 머리글은 굵게 표시하고, 짧은 값은 가운데, 설명은 왼쪽으로 정렬한다.
- 이미지는 `![설명](파일명.확장자)`, 링크는 `[표시 이름](URL)` 형식으로 작성한다.

## 문서 작성 절차

### 1. 기준 확인

1. 작성 기준을 확인한다.
   - 요구사항별 검증 항목
   - 바꿀 수 없는 확정 사항과 제약
   - 변경 대상과 생성 대상
   - 승인된 행동과 영향 범위
2. 문서의 독자, 목적, 유형, 기존 서식을 확인한다.
3. 작업할 문서가 있으면 본문 전체를 읽고, 서식과 문서 구조가 지침에 맞는지 확인한다.
   - 서식 지침과 기존 문서 서식이 충돌하면 작업 전 보고하여 의도된 것인지 확인을 받는다.
   - 기존 문서 내용이 오래되어 새롭게 작성해야 하는 경우 작성할 내용을 보고하고 확인을 받는다.
   - 작업 확정된 작성 내용을 바꿔야 하면 변경할 내용과 근거를 보고하여 확인을 받는다.
4. 지정 항목 수정은 위치와 기대 결과를 확인해 작성하고 완료 절차로 넘어간다.
5. 결과물이 지침 또는 스킬이면 `지침과 스킬 작성 절차` 절을 함께 따른다.

### 2. 파일 작업

- 확인한 작성 기준과 문서 유형에 맞춰 변경 대상과 생성 대상에 문서를 작성한다.

#### 운용 문서 규칙

- 설치, 사용, 문제 해결을 다루는 운용 문서에는 그 절차만 쓴다.
  - 구조와 운용 절차를 순서대로 쓰고, 절차에 쓰는 커맨드와 설명을 함께 적는다.
  - 코드 동작 설명 대신 그 파일을 쓰는 절차 단계에 파일 링크를 둔다.
  - 다른 문서에 있는 절차, 커맨드, 설명은 그 문서 절로 링크한다.

## 지침과 스킬 작성 절차

지침 문서(AGENTS.md, CLAUDE.md)와 스킬 문서(SKILL.md)를 생성하거나 변경할 때 적용한다.
작성 전 확인한 조사 결과를 사용한다.

### 1. 배치 선택

1. 문서 작성 절차의 기준 확인 결과로 지침과 스킬의 배치를 정한다.
2. 유지, 개정, 통합, 신설 중 필요한 처리를 정한다.
   - 사실과 설계 해석을 구분하고 변경 근거와 정의 위치를 연결한다.
   - 같은 작업을 다루는 기존 지침과 스킬이 있으면 해당 문서의 개정 및 통합을 우선 고려한다.
   - 서로 다른 파일이더라도 같은 대상에 주입되는 유사한 문장은 한 파일에만 둔다.
3. 문장의 위치는 작성된 위치 및 실행되는 시점과 일치시킨다.
   - 모든 세션에 적용하는 내용은 공통 지침에 둔다.
   - 특정 에이전트에만 적용하는 내용은 에이전트 지침에 둔다.
   - 특정 작업에만 적용하는 절차 및 예시는 스킬 원본에 둔다.
   - 동일한 의미나 내용은 하나의 파일에 정의한다.
     작업할 대상 문서의 주제, 기능과 호출 시점을 먼저 고려한다.
4. 문장별 적용 조건과 이를 뒷받침하는 자료, 해당 위치를 택한 이유를 연결한다.
   - 일반 대화와 프로젝트 작업의 적용 사례를 비교하여 적용 범위에 맞게 문장을 나눈다.
   - 기존 위치를 바꾸면 종전 분류가 성립하지 않는 근거를 명시한다.
   - 미확정 조건은 확인이 필요한 항목으로 기록한다.
5. 문서 사이 참조는 아래 기준으로 쓴다.
   - 공통 경로는 경로 목록의 이름으로 참조하고 실행에 필요한 원본과 설정 위치는 정확한 경로로 적는다.
   - 필요한 문장은 문서 안에서 완결하고 같은 파일 안의 절 참조를 허용한다.
   - 대상에 구체적인 명칭이 있으면 경로 대신 그 명칭을 쓴다.
   - 다른 스킬의 절차는 중복해 넣는 대신 작업 대상과 결과 기준으로 설명한다.
   - 실행 입력과 원본을 찾는 데 필요한 경로는 기준 루트와 함께 명시한다.

### 2. 파일 작업

- 배치 선택 결과를 기준으로 변경 대상과 생성 대상의 지침 또는 스킬을 작성한다.

#### 본문 규칙

- 본문은 500줄 이하로 작성한다.
- 문장은 공백 포함 100자 이내로 어순을 명확하게 작성한다.
- 파일명, 스킬명, 다른 파일의 절 또는 내용을 언급하는 문장은 제거한다.
- 전체 저장소 범위에서 서식 구조, 동일한 역할의 용어, 동일한 역할의 속성 또는 형식을 통일한다.
- 문장은 긍정형으로 작성한다.
  - 적용 조건, 수행 행동, 확인 가능한 완료 기준을 작성한다.
  - `중요한`, `쉬운`, `긴` 등 판정 기준이 없는 표현을 구체적인 기준으로 바꾼다.
  - 제한이 필요한 문장은 허용 대상, 적용 조건, 대안 행동으로 작성한다.
- 보고, 검토 목적의 응답 또는 문서 생성을 지시하는 문장에는 작성 템플릿을 포함한다.
- 특정 에이전트를 지칭해야 하는 경우 역할 이름으로 작성한다.

#### 본문 구조 규칙

- 규칙은 목록 또는 단순 문단으로 구성하며, 절차는 번호 목록으로 구성한다.
- 지침과 스킬 본문은 절차 절을 중심으로 작업하면서 규칙 절을 중간에 참고할 수 있도록 작성한다.
- 절 내용이 30줄을 초과하면 내용 분리 기준을 두고 각 하위 절에 위치시킨다.  
  새로 만든 하위 절 간 연관성이 낮다면 기존 상위 절을 삭제한다.
- 모든 절차에 적용되는 규칙은 본문 최상단에 두며, 각 규칙은 우선 순위로 배치한다.  
  내용이 길어지는 경우 하위 규칙 절을 둘 수 있다.
- 특정 절차에서만 적용되는 규칙은 5줄 이하인 경우 해당 절의 최상단에 위치시키고, 그렇지 않으면 해당 절의 최하단 하위 규칙 절에 둔다.
- 절차는 해당 절의 번호 목록 또는 해당 절의 하위 절차 절에 둔다.

- 최상위 규칙 절 제목: `<범주> 규칙`
- 규칙 절의 하위 규칙 절 제목: `<범주>`
- 최상위 절차 절 제목: `<범주> 절차`
- 절차 절의 하위 절차 절 제목: `<번호>. <단계명>`, 번호는 `n.n.n.` 단계까지 둘 수 있다.
- 절차 절의 하위 규칙 절 제목: `<범주> 규칙`

#### 스킬 형식 규칙

- 스킬 문서는 아래 기준으로 작성한다.
  - `name`: 영문 소문자, 숫자, 하이픈으로 64자 이하로 작성한다.
  - `description`: 사용 시점과 작업 내용 정보를 배치한다.
    키워드가 겹치는 다른 스킬이 있는지 파악하여 혼동을 주지 않도록 호출 대상 요청을 작성한다.
  - 본문 전체는 다음과 같이 구성한다.
    - `## 목적`(선택): 1개
    - `## <공통 규칙 이름> 규칙`(선택): 1개
    - `## <독립 작업 이름> 절차`: n개
    - `## Template`(보고 스킬, 문서 생성 스킬 필수): 결과물 템플릿
    - `## 결과물 예시`(선택): 구체적인 결과물 예시
  - 하위 절차 절 이름은 `### <번호>. <하위 작업 이름>`으로 규칙이나 절차 텍스트 없이 쓴다.

## 완료 절차

1. 문서 전체를 요구와 서식 및 작성 기준으로 대조해 수정한다.
   기존 규칙의 적용 예외로 확정한 내용과 서식은 확정 기준으로 대조한다.
2. 변경 시각 속성이 있으면 현재 KST로 갱신하고 임시 산출물을 제거한다.
3. 변경한 내용 전체와 diff를 반환한다.
   지정 밖 충돌 수정은 변경 전후 내용과 근거를 함께 적고 남은 검증을 구분한다.

## Template

```markdown
- 변경 위치: <파일:행>
- 작성 근거: <요구와 원문>
- 변경 내용: <변경 전후와 diff>
- 대조 결과: <기준별 충족 여부와 근거>
- 남은 문제: <항목과 확인 방법 | 없음>
```
