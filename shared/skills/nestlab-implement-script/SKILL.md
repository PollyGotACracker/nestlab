## 구현 절차

### 1. 기준 확인

1. 구현 기준을 확인한다.
   - 요구사항별 검증 항목
   - 바꿀 수 없는 확정 사항과 제약
   - 변경 대상
   - 승인된 행동과 영향 범위
2. 모듈 위치, 파일명, 영향 범위 등 구현 기준의 타당성을 검토한다.
3. 검토 결과 구현 기준을 바꿔야 하는 것으로 판단되면 작업을 멈추고 바꿀 항목과 근거를 보고한다.
4. 지정된 수정 항목만 고치는 작업인 경우 항목마다 수정 위치와 기대 결과를 확인하고,
   기대 결과에 일치하도록 작업한 뒤 `3. 대조` 단계로 넘어간다.

### 2. 구현

1. 요청받은 작업 내용, 구조, 방식, 결과물을 변경 범위로 둔다.
2. 사용자와 다른 작업자의 기존 변경은 승인된 수정 대상과 구분해 보존한다.
   수정 직전에 `git status --ignored`로 대상의 추적 상태를 확인하고, 추적 밖이나 무시 대상 파일은 같은 폴더에 `.bak` 사본을 만든 뒤 수정한다.
3. 변경 범위를 기준으로 스크립트 변경 또는 추가 작업을 수행한다.
4. 주석 규칙을 적용하여 주석을 추가한다.
5. 테스트 코드 규칙을 적용하여 테스트 케이스를 추가한다.
6. 이번 변경과 충돌하는 경로 참조 또는 문서를 추가로 발견한 경우 파일을 해당 턴에 수정한다.  
   수정 내용과 사유는 작업 완료 후 보고한다.
7. 이미 확인한 결과는 적용되는 에이전트별 입력 경계 안에서 재사용한다.
   변경, 누락, 충돌이 생긴 범위만 다시 확인해 기존 결과 위치와 추가 확인 사유를 남긴다.

#### 구현 규칙

- 외부 저장소 이름을 코드나 주석에 작성하지 않고, 간접적으로 가리키는 명칭을 사용한다.
- 사용자 원문을 그대로 옮기지 않고 요약하거나 가공한다.
- 주석:
  - 코드 동작 설명은 해당 코드의 주석에 둔다.
  - 주석에서 대상에 구체적인 명칭이 있으면 경로 대신 그 명칭을 쓴다.

#### 테스트 코드 규칙

- 테스트 케이스는 요구사항의 검증 항목을 확인하는 것을 우선으로 한다.
- 문서 및 지침에 포함된 내용 확인, 단순 설정값 확인은 테스트 작성에서 제외한다.
- 엣지 케이스는 검증 항목과 직접 관련된 경계 조건 중 기대 결과가 명확한 경우 추가한다.
- 동일한 동작을 검증하는 엣지 케이스는 대표 테스트 케이스로 통합한다.
- 테스트 대상이 변경되었거나 사라져서 충돌하는 테스트가 있다면 해당 턴에 수정하고 수정 내용과 사유를 보고한다.  
  대상이 보존된 테스트의 충돌은 설계 또는 구현 결함으로 재구현 대상이다.

### 3. 대조

1. 결과를 반환하기 전 요구사항과 완료 기준 전체를 실제 결과와 대조한다.
2. 수정 후 변경 위치와 참조 대상을 대조한다.
3. 작업 과정에서 사용된 임시 산출물을 제거한다.

### 4. 재구현

1. `FAIL`과 `미측정` 항목마다 아래 조건을 확인한다.
   - 재구현이 승인 범위 안에 있다.
   - 기존 요구사항, 제약, 완료 기준 안에서 해결할 수 있다.
   - 전달된 작업 기준의 재구현 허용 범위 안에 있다.
2. 조건을 모두 충족하면 즉시 재구현한 뒤 재판정한다.
3. 조건을 충족하지 못한 기준은 재구현을 멈추고 해당 기준, 원인, 유효한 대안을 제시한다.

### 5. 완료 보고

1. 작성 범위의 기준이 `PASS`이면 결과물 경로, 구현 근거와 대조 결과를 반환한다.
   검증 담당의 실행이 필요한 `미측정` 항목은 남은 검증으로 함께 반환한다.
2. 수행 불가, 조건 미충족, 완료 기준 오류는 근거를 확인한 뒤 보고한다.
3. 응답 회고 요청을 받으면 반복된 실수와 다른 대화에도 적용 가능한 개선안을 제시한다.

## Template

```markdown
## 완료 보고

| **기준** | **실제 결과** |        **판정**        |
| :------- | :------------ | :--------------------: |
| <기준>   | <실제 결과>   | <PASS / FAIL / 미측정> |

- 명세와 다른 처리: <변경 위치, 명세 문구, 실제 처리와 사유 | 없음>
```
