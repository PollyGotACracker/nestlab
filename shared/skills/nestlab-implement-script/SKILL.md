## 공통 규칙

- 코드 내 에이전트 지침 주입 기능이 있는 경우, 지침 작성 관련 스킬과 지침을 호출하여 확인한 후 해당 기준을 준수한다.
- 목적을 달성할 수 있는 최소한의 코드로 동작하도록 구현한다.
- 기존 코드에서 작업 목표와의 충돌이 존재하는 경우, 유지하라는 별도 지시가 없다면 변경 또는 제거한다.
- 함수 내부의 구조와 동작을 직접적으로 설명하는 주석 대신 스크립트를 읽었을 때 이해할 수 있도록 구현한다.
- 기존에 약속되거나 사용된 동일 대상의 용어와 명칭을 우선적으로 찾아 작성한다.
- 에이전트 언급, 세션 사용자 언급, 세션 및 작업 맥락 등 문서 맥락과 직접적이지 않은 메타 발언을 제거한다.
- 다음은 약속된 명칭, 익명화, 자리표시자 또는 일반화된 표현으로 대체한다.
  - 개인 정보
  - 특정 사용자를 지칭하는 맥락이 아닐 때 사용자명, 닉네임, 이메일
  - 보안 정보
  - 세션 외부 경로
  - 개인 폴더명
  - 로그 파일명과 본문
  - 세션 식별자와 본문
  - 세션의 사용자 메시지
  - 기타 비공개 정보

### 스크립트 작성

### 주석 작성

- 문장 관련 규칙이 있다면 해당 규칙을 준수하여 작성한다.
- 주석에서 대상에 구체적인 명칭이 있으면 경로 대신 그 명칭을 쓴다.
- 향후 작업 계획은 작성 규칙을 준수하여 핵심 내용만 짧게 쓴다.

### 테스트 코드 작성

- 테스트 케이스는 요구사항의 검증 항목을 확인하는 것을 우선으로 한다.
- 문서 및 지침에 포함된 내용 확인, 단순 설정값 확인은 테스트 작성에서 제외한다.
- 엣지 케이스는 검증 항목과 직접 관련된 경계 조건 중 기대 결과가 명확한 경우 추가한다.
- 동일한 동작을 검증하는 엣지 케이스는 대표 테스트 케이스로 통합한다.
- 테스트 대상이 변경되었거나 사라져서 충돌하는 테스트가 있다면 해당 턴에 수정하고 수정 내용과 사유를 보고한다.  
  대상이 보존된 테스트의 충돌은 설계 또는 구현 결함으로 재구현 대상이다.
- hook과 도구를 바꾸기 전에 기준 테스트를 정하고, 변경 뒤 기존 동작의 유지 여부를 확인한다.
  차단 동작을 바꾸면 정상 입력과 차단 입력의 시험을 각각 한 개 이상 둔다.
  요구사항 대상 밖의 기존 판정 줄(if, return)을 삭제하면 결함으로 판정한다.

## 구현 절차

### 1. 기준 확인

1. 구현 기준을 확인한다.
   - 요구사항별 검증 항목
   - 바꿀 수 없는 확정 사항과 제약
   - 변경 대상
   - 승인된 행동과 영향 범위
2. 모듈 위치, 파일명, 영향 범위 등 구현 기준의 타당성을 검토한다.
3. 검토 결과 구현 기준을 바꿔야 하는 것으로 판단되면 작업을 멈추고 바꿀 항목과 근거를 보고한다.
4. 지정된 수정 항목만 고치는 작업인 경우 항목마다 수정 위치와 기대 결과를 확인하고,
   기대 결과에 일치하도록 작업한 뒤 `3. 대조` 단계로 넘어간다.
5. 지정 항목 수정도 호출부, 반환값 소비처와 관련 테스트를 확인한다.
   수정 위치, 기대 결과와 보존할 동작을 구분해 변경한다.
   변경으로 기대 결과가 달라진 테스트를 함께 수정한 뒤 대조 단계로 넘어간다.  
   테스트의 실행은 지시가 있을 경우에 수행한다.

### 2. 구현

1. 요청받은 작업 내용, 구조, 방식, 결과물을 변경 범위로 둔다.  
   기존 파일에 지침 및 요청과의 충돌 사항이 있을 때 작업 후 수정된 사항을 보고한다.
2. 사용자와 다른 작업자의 기존 변경은 승인된 수정 대상과 구분해 보존한다.  
   수정 직전에 `git status --ignored`로 대상의 추적 상태를 확인하고, 추적 밖이나 무시 대상 파일은 같은 폴더에 `.bak` 사본을 만든 뒤 수정한다.
3. 변경 범위를 기준으로 스크립트 변경 또는 추가 작업을 수행한다.
4. 주석 규칙을 적용하여 주석을 추가한다.
5. 테스트 코드 규칙을 적용하여 테스트 케이스를 추가한다.
6. 이번 변경과 충돌하는 경로 참조 또는 문서를 추가로 발견한 경우 파일을 해당 턴에 수정한다.  
   수정 내용과 사유는 작업 완료 후 보고한다.
7. 이미 확인한 결과는 적용되는 에이전트별 입력 경계 안에서 재사용한다.
   변경, 누락, 충돌이 생긴 범위만 다시 확인해 기존 결과 위치와 추가 확인 사유를 남긴다.

### 3. 대조

1. 요구사항마다 변경 파일, 검증 커맨드, 기대 결과와 실제 결과를 대조한다.
2. 스크립트 및 지침(지침 주입 기능이 있는 경우) 작성 관련 규칙과 실제 결과를 대조한다.
3. 변경 diff를 승인 범위와 대조하고 호출부와 관련 테스트의 반영 여부를 확인한다.
4. 실행 결과가 없는 항목과 생략된 테스트는 통과 항목에서 분리한다.
5. 작업 과정에서 생성된 임시 산출물을 제거한다.

### 4. 재구현

1. `FAIL` 항목과 실행 결과가 없는 항목마다 아래 조건을 확인한다.
   - 재구현이 승인 범위 안에 있다.
   - 기존 요구사항, 제약, 완료 기준 안에서 해결할 수 있다.
   - 전달된 작업 기준의 재구현 허용 범위 안에 있다.
2. 조건을 모두 충족하면 즉시 재구현한 뒤 재판정한다.
3. 조건을 충족하지 못한 기준은 재구현을 멈추고 해당 기준, 원인, 유효한 대안을 제시한다.

### 5. 완료 보고

1. 작성 범위의 기준이 `PASS`이면 결과물 경로, 구현 근거와 대조 결과를 반환한다.
   검증 담당이 실행할 항목은 실행 조건과 커맨드를 남은 검증으로 함께 반환한다.
2. 수행 불가, 조건 미충족, 완료 기준 오류는 근거를 확인한 뒤 보고한다.
3. 응답 회고 요청을 받으면 반복된 실수와 다른 대화에도 적용 가능한 개선안을 제시한다.

## Template

```markdown
## 구현 결과

| **기준** | **실제 결과** |        **판정**        |
| :------- | :------------ | :--------------------: |
| <기준>   | <실제 결과>   | <PASS / FAIL / 미측정> |

- 명세와 다른 처리: <변경 위치, 명세 문구, 실제 처리와 사유 | 없음>
```
