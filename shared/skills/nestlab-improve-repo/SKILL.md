## 분석 규칙

- 분석 대상은 읽기와 로컬 검증으로 확인하고, 작성 범위는 요청한 개선 보고서로 정한다.
- 수정안 적용, 삭제, 설치, 전역 설정 변경과 외부 전송은 별도 승인 범위로 구분한다.
- 결함과 취향에 따른 제안을 구분한다.
- 파일 크기와 규칙 수는 탐색 지표로 사용하고, 낭비 판정은 실제 영향과 연결한다.
- 같은 원인의 증상은 하나의 항목으로 결합하고, 적용 조건이 다른 규칙은 각각 평가한다.

## 저장소 분석 절차

### 1. 범위 확인

1. 입력 인수로 저장소 경로, 분석 목적, 분석 범위와 보고서 저장 경로를 받는다.
   보고서 저장 경로는 `.md` 파일의 절대 경로 또는 저장소 루트 기준 상대 경로로 지정한다.
   e.g. `저장소=. 범위=전체 보고서=reports/repo-improvement.md`
2. 보고서 저장 경로가 생략되면 해당 인수를 질문하고, 독립적인 읽기 조사는 계속한다.
   지정 경로의 쓰기 권한과 기존 파일을 확인한다.
   기존 파일은 덮어쓰기 승인이 있을 때 갱신하고, 그 외에는 새 경로를 확인해 원본을 보존한다.
3. 저장소 지침, 진입점과 테스트 명령을 확인하고 대상 목록을 구성한다.
   - 코드, 공용 모듈과 의존성
   - 지침, 역할과 스킬
   - hook, 도구와 설정
   - 설치 원본과 연결 상태
   - 테스트, CI와 운영 문서
4. 생성물과 외부 의존성은 목록 중심으로 확인하고, 결함의 근거가 있는 부분만 읽는다.
5. 전역 설정과 설치본은 허용된 읽기 범위에서 원본과 대조한다.

### 2. 근거 수집

1. 경로와 기호를 검색해 진입점, 호출부, 반환값 소비처와 관련 테스트를 추적한다.
2. 지침과 스킬은 제목 및 description으로 후보를 찾고, 관련 본문만 읽는다.
3. 로그는 관련 작업과 기간으로 제한해 읽고, 결론의 근거는 추적 대상 원본과 연결한다.
4. 외부 사실은 실제 버전에 맞는 공식 문서와 변경 기록에서 확인한다.
5. 점검할 범주에 해당하는 아래 참고 자료의 본문을 읽고, 현재 환경과 적용 조건을 대조한다.
   보고서에는 발견 사항의 근거로 사용한 자료의 제목, URL, 열람 범위와 해당 발견 사항의 관계를 기록한다.
   본문을 열람할 수 없으면 같은 주제의 공식 대체 자료를 찾고, 확인 범위를 명시한다.
   여러 기관의 자료를 비교하고, 특정 제품의 권고는 해당 제품과 버전에서만 적용한다.
   - [컨텍스트 구성][context]: 상시 주입과 필요 시 조회의 비용 및 정보 손실
   - [도구 설계][tools]: 도구 구분, 응답 범위와 실행 지표
   - [Agent 평가][evals]: 실제 결과, 실행 기록과 균형 잡힌 테스트
   - [다중 Agent 운영][multi]: 병렬화 이익과 조정 비용
   - [스킬 규격][skills]: 메타데이터와 단계적 로딩
   - [기술 점검 보고서 구성][audit]: 범위, 발견 사항, 개선 조치와 재검증 결과
   - [코드 검토 기준][review]: 설계, 기능, 복잡도와 테스트의 적절성
   - [안정적 재시도][retry]: 시간 제한, 재시도 횟수, backoff와 멱등성
   - [보안 개발 기준][security]: 취약점 예방, 검증과 원인 재발 방지
   - [운영 관측 지표][monitoring]: 지연 시간, 트래픽, 오류와 자원 포화

### 3. 코드와 운영

1. 코드 검토 기준을 바탕으로 중복 구현, 미사용 코드와 추상화의 필요성을 확인한다.
   호출부, 공개 인터페이스, 동적 로딩과 설치 경로를 조사해 제거할 때의 영향을 판단한다.
   공용 함수와 표준 기능의 재사용 후보는 기존 검증 및 오류 처리의 보존 여부로 비교한다.
2. 반복 I/O, 전체 탐색과 자원 해제 누락은 호출 횟수, 처리량과 지연 시간으로 확인한다.
   운영 관측 지표를 참고해 오류율과 자원 사용량을 함께 기록하고 병목 위치를 특정한다.
3. 안정적 재시도 기준에 따라 시간 제한, 최대 횟수, backoff와 멱등성을 확인한다.
   중복 요청, 부분 실패와 동시 실행에서 상태 경쟁 및 부수 효과를 재현한다.
4. 의존성 버전, 설정 기본값, 설치 절차와 문서의 설명을 실제 실행 결과와 대조한다.
   배포와 설정 변경 실패 시 원상 복구 절차 및 데이터 호환성을 확인한다.
5. 보안 개발 기준에 따라 신뢰 경계의 입력 검증, 권한과 비밀 노출을 확인한다.
   파일 덮어쓰기와 삭제의 원자성, 실패 시 데이터 보존 및 복구 경로를 검사한다.
6. 테스트는 정상 결과, 경계값과 실패 경로를 검사하는지 확인한다.
   환경 의존 실패와 제품 결함을 구분하고, 재현 입력에 대응하는 회귀 검증을 정한다.
7. 개선 항목마다 원본 위치, 관측 결과와 참고 자료의 적용 기준을 연결한다.
   현행 유지와 최소 변경을 비교하고, 예상 효과는 실측 결과와 구분한다.
   권고와 다른 구현도 요구사항과 실행 결과를 충족하면 그 근거를 기록한다.

### 4. 토큰과 실행 비용

1. 상시 지침, 스킬 메타데이터, 도구 정의와 필요 시 읽는 본문의 로딩 시점과 주입 경로를 구분하고 크기를 측정한다.
2. 같은 내용의 재주입, 반복 조회, 과도한 도구 출력과 잘린 결과의 재조회를 찾는다.
3. 재승인, 재작성, 실패 재시도와 중복 위임을 해당 실행 기록 및 원인과 연결한다.
4. 이용 가능한 사용량에서 입력, 출력, 캐시와 하위 Agent의 토큰을 구분해 집계한다.
   제공자가 보고한 총량과 세부 항목의 포함 관계를 확인해 중복 합산을 방지한다.
5. 토큰 실측이 없으면 문자 수, 바이트 수와 호출 수를 대리지표로 표시한다.
   토큰 추정값은 tokenizer, 모델과 계산 방법을 함께 적는다.
6. 비용은 측정일의 요금과 사용량 기준으로 계산하고, 구독 한도와 API 비용을 구분한다.
7. 완료한 작업당 비용, 성공률, 소요 시간과 재작업을 함께 평가한다.
   캐시는 과금 비용과 컨텍스트 점유량을 나눠 비교한다.
8. 병렬 실행은 탐색 범위와 시간 이익을 중복 탐색, 문맥 복제와 조정 비용에 대조한다.

### 5. 지침과 스킬

1. 규칙마다 주입 위치, 적용 대상, 발동 조건, 행동과 판정 기준을 비교한다.
2. 충돌은 같은 입력에서 동시에 충족할 수 없는 문장과 실제 우선순위를 제시한다.
3. 동일 행동의 중복 지시, 순환 참조와 승인 또는 완료 조건의 순환 의존을 찾는다.
4. 스킬의 호출 조건 중복, 잘못된 자동 선택과 필요한 호출의 누락을 확인한다.
5. 절차의 목적과 각 단계의 효과를 대조하고, 같은 근거를 반복 확인하는 비용을 평가한다.
6. 원본과 설치본의 차이, 끊어진 연결과 런타임별 도구 입력 차이를 확인한다.
7. 중복 규칙과 불필요한 상시 주입의 통합, 축약 또는 분리 후보를 분석하고, 유지할 정보와 행동, 보안 제약 및 예상 감소량을 제시한다.

### 6. 하네스

1. hook과 도구의 입력, 선행 분기, 차단 판정, 반환값 소비와 상태 기록을 추적한다.
2. 실제 runner의 도구 스키마 및 이벤트와 검사 코드의 가정을 대조한다.
3. 위반 입력과 정상 입력을 함께 실행해 누락 차단과 오탐 차단을 구분한다.
4. 경계값, 빈 입력, 잘못된 입력, 재실행과 동시 실행을 관련 위험에 맞게 확인한다.
5. 검사 중복, 느린 처리, 종료 조건 누락과 승인 또는 재작성 반복을 확인한다.
6. 공통 보안 검사와 역할별 검사, 오류 시 허용 또는 차단 동작을 구분한다.
7. 목적이 유효한 하네스는 정상 작업을 허용하는 재설계안을 우선 비교한다.
   제거안은 목적의 소멸 또는 대체 수단과 회귀 위험을 근거로 제시한다.

### 7. 검증과 우선순위

1. 기존 검사와 부작용 없는 재현으로 가설을 검증하고 명령, 입력과 종료 코드를 기록한다.
   쓰기나 외부 호출이 있는 테스트는 격리 및 승인 범위에 맞게 실행한다.
2. 정적 결함, 실제 재현과 모델 행동의 실측을 각각 구분한다.
   모델 호출이 필요하면 대상과 비용의 승인 범위를 확인하고, 범위 밖이면 사후 실측 계획을 적는다.
3. 개선 전후 비교는 같은 작업, 모델, 설정과 입력을 기준으로 설계한다.
   반복 횟수와 변동을 기록하고, 단일 실행의 차이는 관측값으로 한정한다.
4. 개선안은 원인, 최소 변경, 유지할 동작과 회귀 검증을 연결한다.
   대안이 있으면 현행 유지와 비교해 효과 및 변경 비용을 적는다.
5. 우선순위를 영향과 발생 조건으로 정하고, 근거 확실성과 수정 비용을 따로 표시한다.
   - P0: 진행 중인 정보 노출, 데이터 손실 또는 핵심 작업의 전면 중단
   - P1: 재현한 기능 결함, 정상 작업 차단 또는 반복되는 고비용 재작업
   - P2: 특정 조건의 비효율 또는 유지보수 부담
   - P3: 동작 영향이 확인되지 않은 선택적 정리
6. 가설은 재현과 원본 확인으로 검증한 뒤 확정 결함과 개선 후보로 분류한다.

### 8. 보고서 저장

1. 템플릿에 따라 범위별 확인 결과와 우선순위별 발견 사항을 Markdown으로 작성한다.
2. 각 항목에 원본의 파일:행, 최소 인용과 재현 결과 또는 외부 링크를 붙인다.
3. 항목 수, 출처, 원인 중복, 실행 결과와 예상 효과의 구분을 대조한다.
4. 입력 인수로 확정한 보고서 경로에 저장하고, 파일 존재와 작성 내용의 일치를 확인한다.
   응답에는 보고서 링크와 핵심 발견을 반환한다.

## Template

```markdown
# 저장소 개선 보고서

## 결론

- 우선 처리: <발견 ID, 원인과 필요한 조치>
- 전체 판정: <확정 결함과 개선 후보의 개수>

## 범위와 조건

- 대상: <저장소, 기준 commit과 미커밋 변경>
- 환경: <OS, runner, 도구와 확인한 모델 설정>
- 범위: <조사한 경로와 기준, 제외 범위 및 사유>
- 확인 결과: <범주별 관측 사실과 근거>
- 측정 기준: <작업, 입력, 기간, 단위와 반복 횟수>

## 발견 사항

### <ID>. <구체적인 문제>

- 분류: <코드 | 토큰 | 지침 | 스킬 | 하네스 | 운영>
- 판정: <확인 사실 | 추론>
- 우선순위: <P0~P3와 영향 및 발생 조건>
- 근거 확실성: <실제 재현 | 정적 확인>
- 위치와 근거: <원본 파일:행, 최소 인용 또는 링크>
- 기대와 실제: <기대 결과와 관측 결과>
- 재현: <환경, 입력, 명령, 종료 코드와 관측값>
- 원인: <사실, 추론 과정과 반대 근거>
- 영향: <실패, 노출, 재작업과 측정 비용>
- 개선안: <최소 변경, 유지할 동작과 필요 시 대안>
- 비용과 위험: <수정 범위, 작업량, 의존성과 회귀 위험>
- 예상 효과: <실측과 구분한 추정, 계산식과 가정>
- 완료 기준: <같은 조건의 재검증과 성공 조건>

## 실행 확인

- <검사와 입력>: <종료 코드, 관측 결과, 입증 범위와 한계>
```
