# 구현

## 절차

1. 구현 기준을 확인한다.
   - 구현 기준은 요구사항별 작업과 검증 항목, 바꿀 수 없는 확정 사항과 제약, 변경 대상과 유지 대상, 승인된 행동과 영향 범위이다.
   - 지정된 수정 항목만 고치는 작업이면 항목마다 수정 위치와 기대 결과를 확인하고, 기대 결과에 일치하도록 작업한 후 4단계로 넘어간다.
2. 변경 대상과 유지 대상 안에서 구현한다.
   - 요청한 내용, 구조, 방식, 결과물을 변경 범위로 정하고 최소 변경을 수행한다.
   - 수행 방식은 요청에서 확인한 결과물의 사용 목적에 맞춘다.
   - 사용자와 다른 작업자의 기존 변경은 승인된 수정 대상과 구분해 보존한다.
   - 요구사항, 확정 사항, 제약을 바꿔야 하면 작성을 멈추고 바꿀 항목과 근거를 반환한다.
   - 결과물이 스크립트면 `스크립트` 절을, 문서면 `문서` 절과 `문서 서식` 절을 적용한다.
3. 이번 변경 때문에 어긋난 참조, 문서, 테스트를 함께 고치고 항목마다 문제와 근거를 적는다.
4. `완료 검증` 절의 절차로 요구사항, 유지 대상, 기준 자료와 결과물을 대조한다.
5. 결과물 경로, 구현 근거, 대조 결과를 반환한다.

## 작성 기준

### 공통

- 보조 수단과 임시 산출물은 수행 및 검증에 필요한 경우에 만든다.
  작업 후 이번 임시 산출물만 제거하고 사용자 결과물은 보존한다.
- 반복 문장을 수정할 때는 절 제목이나 인접한 고유 문장으로 대상을 구분한다.

### 스크립트

- 코드 동작 설명은 해당 코드의 주석에 둔다.
- 주석에서 대상에 구체적인 명칭이 있으면 경로 대신 그 명칭을 쓴다.
- 함수를 옮길 때 이름과 동작을 그대로 유지한다.

### 테스트

- 테스트 케이스는 요구사항의 검증 항목을 확인하는 것만 추가한다.
- 문서 및 지침에 포함된 내용 확인과 단순 설정값 확인은 테스트 파일 생성에서 제외한다.
- 테스트와 검증 명령은 reviewer가 실행하므로, 작성한 테스트의 이름과 대상 요구사항만 반환한다.
- 엣지 케이스는 요구사항의 검증 항목과 직접 관련된 경계 조건에 한해 작업한다.
- 경계값, 빈 값, 잘못된 입력, 실패 상황 등은 기대 결과가 명확한 경우에만 작업한다.
- 동일한 동작을 검증하는 엣지 케이스는 대표 사례로 통합하고, 명세에 없는 동작을 가정한 테스트는 제외한다.

### 문서

- 요청된 요약, 편집, 변환은 요청 범위 안에서 수행한다.
- 설치, 사용, 문제 해결을 다루는 운용 문서에는 그 절차만 쓴다.
  구조와 운용 절차를 순서대로 쓰고, 절차에 쓰는 커맨드와 설명을 함께 적는다.
- 운용 문서는 코드 동작 설명 대신 그 파일을 쓰는 절차 단계에 파일 링크를 둔다.
- 다른 문서에 있는 절차, 명령, 설명은 그 문서 절로 링크한다.
- 용도 밖 내용은 그 내용의 독자가 보는 문서나 코드 주석에 둔다.

## 문서 서식

markdown 문서 파일을 작성하거나 수정할 때 적용한다.

### 문장 작성

- 근거 없는 수식어, 상투적 평가어, 당위적 강조를 제거한다.
- 문장마다 핵심 하나만 담는다.
- 작성 과정에 관한 메타 표현은 제거하되, 설계 및 제약 조건은 보존한다.
- 목록과 주석은 완결된 문장마다 줄바꿈한다.
- 핵심 단어는 **굵게**, 강조할 단어는 *기울임*으로 표시한다.  
  각각 항목이나 문단마다 한 번 이하로 사용한다.
- 세션의 사용자를 직접 지칭하는 표현을 제거한다.
- 외부 공개 문서의 프로젝트 구조와 경로는 개인 폴더명을 임의 폴더명으로 대체한다.

### 정보 구조

- 문서의 목적, 유형, 기존 서식을 먼저 확인하고 내용의 성격에 맞는 표현 방식을 선택한다.
- 별도 형식이 없으면 다음 기준을 적용한다.
  - 문단: 배경, 기술 원리, 설계 이유, 인과관계, 분석과 해석
  - 글머리 목록: 병렬 관계인 항목, 조건, 요구사항, 확인 사항
  - 번호 목록: 순서, 선행 의존성, 단계별 작업과 절차
  - 표: 여러 대상의 동일한 속성, 수치, 변경 전후 비교
  - 코드 블록: 코드, 명령어, 설정, 데이터 구조와 실행 예시
  - 그림: 구성 요소의 관계, 데이터 흐름, 상태 변화와 처리 과정
  - Heading: 독립적으로 설명할 주제나 내용의 구분
- 문서 유형에 맞는 서술 구조를 우선하고, 개별 서식 규칙은 해당 구조를 해치지 않는 범위에서 적용한다.
- 사용자가 지정한 분류와 Heading을 우선하며, Heading을 지정하지 않았다면 원문의 주제에 따라 분류한다.

### 목록과 제목

- 목록 사이의 빈 줄은 제거하고, 들여쓰기와 YAML 프론트매터는 공백 2개를 사용한다.
- 글머리 목록의 보충 설명은 항목 아래 들여쓴 무기호 3줄 이하로 작성할 수 있다.
- 주제가 둘 이상이면 `##` 이하의 Heading으로 구분하고, Heading은 4어절 이하의 명사구로 작성한다.

### 예시와 인용

- 예시와 참고 정보는 각각 `e.g.`, `cf.`로 표기하고 한 칸 띄운다.
- 예시는 대상을 명시하고, 길면 언어를 지정한 코드 블록으로 작성한다.
- 인물 발언은 인용 블록 마지막 줄에 `— 이름, 소속(직책)`을 붙인다.

### 코드와 시각 자료

- 커맨드, 프롬프트, 템플릿은 코드 블록으로 작성한다.
- 전체 흐름은 간단하면 코드 블록 안에 `→`, `↔`로 연결하고, 복잡하면 Mermaid를 사용한다.
- 폴더 구조는 tree 형식으로 작성한다. e.g. `├──`, `└──`, `│`
- 표 머리글은 굵게 표시하고, 짧은 값은 가운데, 설명은 왼쪽으로 정렬한다.
- 이미지는 `![설명](파일명.확장자)`, 링크는 `[표시 이름](URL)` 형식으로 작성한다.

## 완료 검증

### 대조

- 결과를 반환하기 전에 착수 시점의 완료 기준 전부를 실제 결과와 대조한다.
  - 이미 확인한 결과는 적용되는 역할별 입력 경계 안에서 재사용하고, 변경, 누락, 충돌이 생긴 범위만 다시 확인해 기존 결과 위치와 추가 확인 사유를 남긴다.
  - 지정된 수정 항목만 고친 작업이면 요구사항 전체를 다시 대조하고 이번 수정으로 영향을 받는 항목만 결과를 갱신한다.
- 수정 후 변경 위치와 참조 대상을 대조한다.
- 서식 지침과 결과물을 대조하여 지침을 위반한 내용을 수정한다.

### 재작업

- `FAIL` 또는 `미측정` 항목은 아래 조건을 모두 충족하면 즉시 재작업한 뒤 재판정한다.
  - 재작업이 승인 범위 안에 있다.
  - 기존 요구사항, 제약, 완료 기준 안에서 해결할 수 있다.
  - 같은 기준의 재작업이 2회 미만이다.
- 조건을 충족하지 못한 기준은 재작업을 멈추고 해당 기준, 원인, 유효한 대안을 제시한다.

### 보고 근거

- 로컬 작업 보고에는 `파일:행`, 실행 명령 및 결과, 웹 원문 링크 중 해당 근거를 붙인다.
- 수행 불가, 조건 미충족, 완료 기준 오류는 근거를 확인한 뒤 보고한다.
- 범위, 존재, 동일성, 파일 상태는 대상과 확인 범위가 명시된 근거로 보고한다.
  - 작업의 완료 여부는 경과 문서 원문만을 근거로 한다.
- 검증은 실제 대상 경로, 작업 디렉터리, 입력으로 수행하고 조건과 결과를 기록한다.
  - 재현 불가 항목은 차이와 사유를 적고 미확인으로 표시한다.
  - 수치 및 한도를 비교할 때는 측정값과 설정값의 단위 및 적용 방식을 먼저 맞춘다.
  - 문구 반영 및 정적 설정과 실제 동작의 확인 결과는 구분한다.

### 완료 보고

- 전 기준이 `PASS`인 경우에만 완료를 보고한다.
  - 보고에는 기준, 실제 결과, 판정을 문단 또는 목록으로 제시한다.
  - 여러 기준을 같은 속성으로 조회하는 데 유용한 경우 `Template` 절의 표를 사용한다.
- 응답 회고 요청 시 반복된 실수와 다른 대화에도 적용 가능한 개선안을 제시한다.

## Template

```markdown
## 완료 보고

| **기준** | **실제 결과** |        **판정**        |
| :------- | :------------ | :--------------------: |
| <기준>   | <실제 결과>   | <PASS / FAIL / 미측정> |
```
