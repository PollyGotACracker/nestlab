# 설계 문서 작성

## 인수

- `대상`: 첫 쉼표 앞은 파일명, 쉼표 뒤 전체는 사용자가 제공한 사실
  - 파일명은 확장자 없이 적는다.
  - 쉼표가 없으면 전체를 대상 기능으로 보고 파일명만 요구한 뒤 멈춘다.
  - 대상이 비어 있으면 파일명과 대상 기능을 요구하고 멈춘다.
- `결과`: 설계 문서를 만들 폴더 또는 파일 위치
  - 폴더가 없으면 만든다.
  - 현재 레포 안의 파일은 `결과`가 그 위치를 지정할 때만 만들거나 수정한다.

## 절차

1. 입력을 해석한다.
   - 사용자 사실에서 대상 기능의 범위, 요구사항, 택한 방식, 고려했다 버린 대안, 제약 조건, 구현 이유, 환경, 시도한 작업을 추출한다.
   - 사용자가 이미 제공한 항목은 질문 없이 그대로 쓴다.
2. 조사한다.
   - 대상 기능과 관련된 코드만 읽고, 레포 전체 탐색은 생략한다.
   - node_modules, vendor, dist, build, .venv, 락 파일은 읽지 않고 건너뛴다.
   - 읽을 것
     - 해당 기능의 진입점과 호출 경로
     - 인터페이스 정의(함수 시그니처, 타입, 스키마, 엔드포인트)
     - 이 기능이 의존하는 외부 라이브러리와 그 버전
     - 관련 설정값과 환경변수
     - `git log --oneline -- <경로>` 실행 결과
   - 로그 출력이 200줄을 넘으면 그 사실을 알리고 좁히는 방법을 사용자에게 묻는다. 임의로 자르지 말고 사용자 답으로 범위를 정한다.
3. 웹 검색은 아래 범위로 한정한다.
   - 사용 중인 라이브러리와 프레임워크의 권장 패턴과 그 근거: `## 구조` 또는 `## 결정과 근거`에 반영
   - 관련 라이브러리의 기본 동작, 기본값, 버전별 변경: 해당 내용이 나오는 절에 반영
   - 이 문제 영역의 알려진 접근법과 각각의 트레이드오프: `## 결정과 근거`의 비교 근거로만 반영
   - 설계 이해에 필요한 중요 개념 설명: 개념이 처음 나오는 절에 한두 문장으로 반영
   - 커맨드와 설정 항목 설명: 해당 항목 바로 아래에 반영
   - 검색 전에 의존성 파일에서 라이브러리의 실제 버전을 확인하고 그 버전의 문서를 먼저 본다.
   - 공식 문서, 릴리스 노트, 이슈 트래커를 먼저 보고 블로그는 보조로만 쓴다.
   - 검색으로 가져온 문장에는 그 자리에 출처 링크를 단다.
   - 개념 설명은 문서 이해에 필요한 최소 분량으로 쓰고, 튜토리얼 분량은 제외한다.
4. 조사 결과를 출력하고 멈춘다.
   - 읽은 파일 목록
   - 코드에서 확인한 구조: 구성 요소, 데이터 흐름, 외부 의존
   - 관례에서 벗어나 보이는 선택: 위치 `파일:줄`과 특이한 점을 적은 표
   - 사용자 입력에서 추출한 것: 항목별로 넣을 위치
   - 여전히 비는 항목: 없으면 "없음"
   - 비는 항목은 대부분 "왜 그렇게 했는가"와 "무엇을 고려했다 버렸는가"이다.
     이 내용은 코드에 남지 않으므로 사용자만 답할 수 있고, 추측으로 채우지 말고 질문한다.
   - 비는 항목이 있으면 전부 모아 한 번에 묻고, 없으면 질문을 생략한다.
5. 생성할 문서 전문을 조사 결과 뒤에 이어서 출력하고 승인을 받는다.
   - 승인 전에는 파일 생성을 보류한다.
6. 승인을 받으면 `결과` 위치에 파일을 쓰고 경로만 출력한다.
   - 요약이나 소감 없이 경로로 끝낸다.

## frontmatter 값

아래 명령을 실행하고 출력값을 그대로 쓴다. 기억이나 추측으로 채우는 값은 쓰지 말고 명령 출력만 쓴다.

- repo: `basename $(git rev-parse --show-toplevel)`
- updated: `date +%F`

## 규칙

- 파일을 쓰기 전에 파일 전체 내용을 사용자에게 보여주고 승인을 받는다.
- 파일이 이미 있으면 기존 본문을 보존한다.
  본문을 고쳐야 하면 바뀌는 부분과 방식을 사용자에게 먼저 보여주고 승인을 받는다.
- 사용자가 말한 것과 코드에서 확인한 것만 쓴다.
  빈 자리에는 `<!-- TODO: 무엇이 불명확한지 -->`를 남긴다.
- `구조`와 `데이터 흐름`은 코드에서 확인한 현재 모습을 쓴다. 있어야 할 모습은 쓰지 말고 현재 모습만 둔다.
- `결정과 근거`는 사용자가 답한 내용으로만 쓴다.
  코드에서 추론한 내용은 결정 근거로 쓰지 말고, 사용자가 답하지 않은 결정은 소제목만 남기고 `<!-- TODO: 근거 확인 필요 -->`를 넣는다.
- `버린 대안`에는 사용자가 실제로 고려했다고 말한 것만 적는다.
  검색에서 찾은 일반적인 대안은 `결정과 근거` 본문에서 비교 근거로만 언급하고 출처를 단다.
- `구현 이유`, `환경`, `필요 조건과 기술`, `시도한 작업`도 사용자 진술이나 코드에서 확인한 것만 쓰고, 빈 자리에는 TODO 주석을 남긴다.
- `코드 참조`의 파일은 레포 루트 기준 상대경로로 적고, 절대경로는 쓰지 말고 코드에서 실제로 확인한 심볼만 적는다. 없으면 표를 비운다.
- `참고 자료`에는 실제로 열람한 자료만 링크로 적는다.
- `## 메모` 아래는 어떤 경우에도 수정하거나 삭제하지 말고 그대로 보존한다.
- 이모지와 평가 형용사는 쓰지 말고 사실만 적는다.

### 1. 소제목

- `## 결정과 근거` 아래 소제목(`###`)은 결정 하나당 하나씩 둔다.
- `## 구조`와 `## 데이터 흐름` 안의 소제목은 아래 조건을 전부 만족할 때만 쓴다.
  - 그 절이 4문단을 넘는다.
  - 독립적으로 다룰 갈래가 2개 이상이다.
- 조건이 맞지 않으면 소제목 없이 문단으로만 쓴다. 내용이 짧으면 소제목으로 구조를 만들어내지 말고 문단으로 둔다.
- `## 결정과 근거` 안의 소제목은 결정 내용을 서술한 명사구로 쓴다.
  e.g. 좋음 `### 재시도를 고정 간격으로 고정`, 나쁨 `### 재시도 정책 결정`, `### 왜 고정 간격인가`, `### 설계 고려사항`
- `## 구조` 안의 소제목은 구성 요소나 계층의 이름으로 쓴다.
  e.g. 좋음 `### 요청 라우팅 계층`, 나쁨 `### 전체 구조 개요`, `### 아키텍처는 어떻게 되는가`
- 소제목은 평서형 명사구로 쓰고, `분석`, `배경`, `개요`, `정리`, `방법`, `접근`, `고려사항`, `설계`로 끝나는 말은 다른 명사로 바꾼다.
- 소제목만 읽어도 무엇이 결정됐는지 알 수 있어야 한다.

### 2. 서술

- 각 절은 결론부터 쓰고, 배경 설명은 뒤에 둔다.
- 한 문단은 3~5문장이고 한 가지만 다룬다.
- 같은 주제의 세부 요소 여러 개는 목록으로 쓴다.
- 같은 내용을 표현만 바꿔 반복하지 말고 한 번만 쓴다.
- 절 끝에는 요약 문단을 붙이지 말고 마지막 사실에서 끝낸다.
- `데이터 흐름`과 `시도한 작업`만 순서대로 쓰고, 나머지는 중요도 순으로 쓴다.
- 1인칭 표현("나는", "저는")은 빼고 사실만 쓴다.

## 결과물 예시

e.g. 가상 프로젝트 "알림 발송기"의 설계 문서

- 기능, 값, 링크는 예시용 가정이다.
- 코드 조사와 사용자 답이 있어야 실제 값으로 채운다.

```markdown
---
repo: notifier
type: design
updated: 2026-08-29
---

# 알림 발송 재시도 설계

## 구현 이유

발송 실패 알림이 한 번 실패하면 사라져 사용자가 알림을 받지 못했다.

## 범위

발송 실패 시 재시도하는 큐 처리기를 다룬다. 알림 본문 생성과 수신 기기 등록은 제외한다.

## 환경

- Python 3.12, Redis 7.2, Linux 컨테이너

## 필요 조건과 기술

- Redis 접속 정보를 담은 환경변수 `REDIS_URL`
- [redis-py](https://redis.readthedocs.io/) 5.0

## 요구사항

- 발송 실패 알림을 최대 3회 다시 보낸다.
- 3회 실패한 알림은 실패 목록에 보관한다.

## 구조

| 구성 요소     | 책임                         |
| ------------- | ---------------------------- |
| 발송 큐       | 보낼 알림을 순서대로 보관    |
| 재시도 처리기 | 실패한 알림을 다시 큐에 넣음 |
| 실패 목록     | 3회 실패한 알림 보관         |

재시도 처리기는 발송 큐에서 알림을 꺼내 발송하고, 실패하면 시도 횟수를 올려 같은 큐에 넣는다.

## 데이터 흐름

1. 발송 큐에서 알림을 꺼낸다.
2. 발송 API를 호출한다.
3. 성공하면 종료하고, 실패하면 시도 횟수를 1 올린다.
4. 시도 횟수가 3 미만이면 5초 뒤 다시 큐에 넣고, 3 이상이면 실패 목록에 넣는다.

## 결정과 근거

### 재시도를 고정 간격으로 고정

- 택한 것: 5초 고정 간격
- 버린 대안과 이유: 지수 백오프는 사용자가 구현 복잡도 때문에 제외했다.
- 제약: 발송 API가 일시 장애일 때 재시도 3회가 15초 안에 끝난다.

## 시도한 작업

- 지수 백오프를 시험했으나 테스트 시간이 길어져 고정 간격으로 바꿨다.
```
