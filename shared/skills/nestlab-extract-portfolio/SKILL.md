# 포트폴리오 소재 추출

## 목적

- **개발 경험**에서 글로 다룰 질문과 이를 설명할 자료를 찾는다.
  프로젝트 설명은 개별 경험을 이해하는 데 필요한 배경으로 사용한다.
- 코드에서 확인한 구현과 실제 개발 경험을 구분한다.
- 결과물의 독자는 포트폴리오 작성자와 후속 글 작성자이다.

## 대상 저장소

- 대화에서 대상이 명확하면 그 저장소를 사용한다.
  대상이 여러 개이거나 불분명하면 조사할 저장소를 질문한다.

## 절차

1. 조사할 구현과 기록의 범위를 파악한다.
   - 저장소의 적용 지침, 구조, README, 설정에서 주요 기능과 진입점을 찾는다.
   - 사용자가 주제를 정하면 그 범위를 우선하며, 주제 지정이 없으면 주요 기능에서 탐색을 시작한다.
   - Git 저장소이면 기준 커밋과 작업 트리 변경 여부를 기록한다.
   - Git 이력이 없으면 현재 코드와 접근 가능한 기록으로 조사한다.
   - 생성물과 의존성 복사본은 제외하고 비밀 값은 수집 대상에서 제외한다.
2. 현재 구현에서 소재 후보를 찾는다.
   - 아래 현재 구현 탐색 방법에 따라 주요 기능의 실행 흐름을 추적한다.
   - 이 경로는 최초 구현과 변경 이력이 없는 코드도 포함한다.
3. 변경 이력과 관련 기록에서도 소재 후보를 찾는다.
   - 아래 변경과 기록 탐색 방법에 따라 별도의 경험을 찾고 기존 후보의 배경을 보충한다.
   - 기록의 존재 여부와 접근 가능 범위를 확인해 조사 한계를 남긴다.
4. 두 경로에서 찾은 후보를 묶고 근거를 정리한다.
   - 같은 문제나 판단을 다루는 코드, 테스트, 후속 수정은 한 후보로 합친다.
   - 후보마다 발견 경로, 구현 사실, 기록에 담긴 설명, 해석을 나누어 적는다.
   - 후보 선정 기준을 먼저 적용해 글로 다룰 이유가 확인된 항목만 남긴다.
   - 소재 판정 기준에 따라 작성 가능, 추가 확인 필요, 보류를 구분한다.
   - 작성 우선순위를 제안할 때는 확인된 판단이나 배움과 근거의 충실도를 이유로 적는다.
5. 후보별 작성 자료를 Markdown 문서로 저장하고 사용자에게 제시한다.
   - 사용자가 지정한 출력 위치나 저장소의 문서 관례를 따른다.
   - 위치가 불분명하면 새 파일 위치를 제안해 확인한다.
   - 사용자가 정리할 소재를 지정하면 그 범위로 작성한다.
   - 별도 지정이 없으면 선정 기준을 통과한 후보를 판정과 함께 정리한다.
   - 답변이 필요한 후보도 근거와 질문을 담아 문서에 남긴다.
   - 통과한 후보가 없으면 확인한 범위와 선정할 소재가 없다는 결과를 보고한다.
6. 기록으로 알 수 없는 경험을 질문하고 답변을 반영한다.
   - 질문에는 관련 구현과 필요한 이유를 붙여 당시 상황을 떠올릴 수 있게 한다.
   - 실제 선택 이유, 시도한 대안, 개인 기여, 배움 등 작성에 필요한 빈 내용만 질문한다.
   - 독립적인 짧은 질문은 묶고, 뒤의 질문에 영향을 주는 질문은 먼저 확인한다.
   - 답변에 따라 후보의 내용과 판정을 갱신한다.
   - 답변을 기다리는 항목은 추가 확인 필요로 남기고, 다른 후보의 근거 정리를 진행한다.
7. 소재별 주장과 근거 위치를 대조하고 결과를 보고한다.
   - 코드 위치, 기준 커밋, 기록과 사용자 답변의 출처를 확인한다.
   - 테스트 존재와 실행 성공, 기대 효과와 관찰 결과, 팀 성과와 개인 기여를 구분한다.
   - 문서 위치, 정리한 소재, 남은 질문과 확인 한계를 보고한다.
   - 게시글 초안 작성은 이 자료를 입력받는 별도 글 작성 작업으로 다룬다.

## 현재 구현 탐색

1. 주요 기능의 진입점에서 입력, 처리, 상태 변화, 출력 순서로 호출 관계를 읽는다.
2. 흐름 안에서 구체적인 처리 방식을 찾는다.
   - 데이터 처리: 저장, 조회, 변환, 검증과 갱신의 기준
   - 상태와 실행 제어: 작업 분리, 순서, 동시 실행, 취소와 중복 처리 방식
   - 오류 복구: 실패 전파, 재시도, 롤백과 부분 실패 처리 방식
   - 구조와 경계: 모듈의 책임 분리와 외부 서비스 의존성을 다루는 방식
     이 목록은 탐색 단서이며 목록 밖에서도 구체적인 판단을 설명할 구현을 찾으면 조사한다.
3. 발견한 처리의 호출부, 관련 설정, 테스트와 주석을 읽는다.
   - 어떤 상황에서 이 처리가 실행되고, 어떤 동작을 보장하며, 어떤 제약을 갖는지 확인한다.
4. 확인한 동작을 바탕으로 글에서 답할 질문을 만든다.
   - 기술을 사용했다는 설명에서 그 기술로 처리한 구체적인 조건과 선택을 설명하는 질문으로 좁힌다.
   - 현재 구현으로 확인할 수 있는 동작과 사용자에게 확인할 선택 이유를 구분한다.
   - 추가 근거가 없어도 발견한 후보와 필요한 질문을 기록한다.

## 변경과 기록 탐색

1. Git 이력, PR, 이슈, 작업 기록에서 문제 해결, 시도, 선택과 판단 변경의 단서를 찾는다.
   - 커밋 메시지는 검색 단서로 사용하고 실제 diff와 관련 코드를 확인한다.
2. 변경이 있으면 이전과 이후의 동작을 비교한다.
   - 어떤 입력이나 상황에서 결과가 달라지는지 호출부와 테스트로 확인한다.
   - 현재 코드에서 사라진 실패한 시도도 관련 기록이 있으면 후보로 조사한다.
3. 구현 변경이 없는 기록에서도 경험을 찾는다.
   - 실험, 도입 보류, 기술 비교, 협의와 학습 기록에서 실제로 수행한 일과 근거를 확인한다.
4. 경험에서 글로 설명할 질문을 만들고 관련 근거를 연결한다.
   - 문제의 실제 발생 여부와 수정 의도는 기록이나 사용자 답변으로 확인한다.

## 후보 선정

- **선정 조건**: 아래 세 조건을 모두 뒷받침할 구체적인 근거가 있다.
  - 일반적인 사용법을 넘어선 문제: 해당 환경의 제약, 충돌하는 요구, 재현하기 어려운 실패, 예상과 다른 실험 결과 중 설명할 조건이 있다.
  - 설명할 판단: 그 조건에서 무엇을 선택하거나 바꾸었으며 어떤 손익이나 한계가 생기는지 설명할 수 있다.
  - 확인할 자료: 그 문제와 판단을 조사할 코드, 테스트, 실험, 기록이 있다.
- **선정 근거**: 일반적인 사용법에 비해 추가로 고려한 조건과 그로 인해 달라진 구현을 연결해 쓴다.
  - 표준적인 기능이나 도구 사용법만 설명할 수 있는 항목은 제외하고 제외 이유만 짧게 남긴다.
  - 흔한 기술도 구체적인 제약 때문에 달라진 판단과 검증을 설명할 수 있으면 선정한다.
  - 후보 수는 선정 기준을 통과한 실제 항목 수에 맞춘다.
    적합한 소재가 없으면 선정 없음으로 보고한다.
  - 제외한 항목을 상세 작성 자료로 확장하는 작업은 사용자가 해당 항목을 별도로 요청했을 때 수행한다.

## 소재 판정

실패한 시도, 잘못된 이해를 고친 과정, 협업 과정에서 달라진 판단도 아래 기준으로 판정한다.

- **작성 가능**: 후보 선정 기준을 통과했고 아래 세 조건을 설명할 자료가 있다.
  - 구체적인 질문: 어떤 경험을 설명하는 글인지 한 문장으로 표현할 수 있다.
  - 판단이나 탐색: 사용자가 무엇을 고려하거나 시도하고 확인했는지 설명할 수 있다.
  - 뒷받침할 근거: 코드, 변경 이력, 실험 결과, 당시 기록, 사용자 답변 중 해당 자료가 있다.
- **추가 확인 필요**: 선정 조건을 뒷받침할 단서는 있으나 실제 선택 이유나 개인 경험의 확인이 남아 있다.
  부족한 부분을 구체적인 질문으로 적는다.
- **보류**: 확인 결과 설명할 경험이나 판단이 드러나지 않거나 핵심 주장을 뒷받침하기 어렵다.
  보류 이유와 다시 검토할 수 있는 조건을 적는다.

## 작성 자료 항목

### 조사 범위

- 대상 저장소와 기준 커밋
- 작업 트리 변경 여부
- 확인한 코드와 기록의 범위
- 제외 범위와 확인 한계

### 소재 정의

- 가제와 글에서 답할 질문
- 발견 경로와 구현 또는 기록의 단서
- 일반적인 사용법을 넘어서는 조건, 판단과 이를 확인할 근거
- 소재 판정과 그 이유

### 경험 내용

- 경험을 이해하는 데 필요한 배경
- 확인된 계기와 당시 제약
- 사용자의 탐색, 시도, 판단 및 직접 수행한 일
- 실제로 검토한 대안과 선택 이유
- 확인된 결과와 확인 방법
- 한계, 배운 점, 이후 달라진 판단

### 근거 위치

- 코드의 상대 경로, 심볼, 행 번호와 관련 커밋
- 관련 기록의 위치와 사용자 답변의 출처
- 해석과 그 근거
- 부족한 내용과 작성 전 질문

### 항목 사용

- 항목은 자료 수집을 위한 기준으로 사용한다.
  경험에 해당하지 않는 항목은 해당 없음으로 표시한다.
- 사용자가 기억으로 설명한 내용과 코드나 기록으로 대조한 내용은 출처를 구분한다.
- 공개용 글로 옮길 때 필요한 개인 경로와 민감한 식별자의 대체 사항을 표시한다.

## 결과물 예시

e.g. 평범한 구현을 제외하고 별도의 판단이 필요한 실패 상황을 선정한 작성 자료이다.
아래 경로, 커밋, 사용자 답변과 테스트는 모두 결과물 형식을 설명하기 위한 가상 자료이다.

```markdown
# 포트폴리오 작성 자료

## 조사 범위

- 대상 저장소: sample-project
- 기준 커밋: abc1234
- 작업 트리: 변경 없음
- 확인 범위: 캐시, 게시 작업자, 작업 저장소, 관련 테스트와 변경 이력, 외부 API 계약 문서, 사용자 답변
- 제외 범위: 운영 로그와 외부 서비스의 실제 동작

## 제외한 항목

- 캐시 만료 처리: 현재 자료에는 일반적인 만료 처리 이상의 제약이나 판단 근거가 없어 제외했다.

## 소재 1. 결과 불명 재시도

- 가제: 외부 게시 성공 여부를 알 수 없는 상황에서 재시도를 설계한 과정
- 글에서 답할 질문: 외부 게시 후 응답이 유실되거나 작업자가 재시작될 때 중복 게시와 작업 유실을 어떻게 다루었는가?
- 발견 경로: 현재 구현과 실패 재현 테스트
- 선정 이유
  - 추가 제약: 외부 게시 성공과 로컬 완료 기록 사이에 프로세스가 종료될 수 있다.
  - 판단: 외부 API의 중복 방지 키를 작업 기록에 먼저 저장하고 재시도에도 같은 키를 사용한다.
  - 손익과 한계: 자동 복구를 유지하지만 외부 API의 키 보존 기간과 저장된 작업 기록에 의존한다.
  - 근거: 키 저장 순서, 재시작 후 복원 코드, 게시 성공 후 응답 유실을 재현한 테스트
- 판정: 작성 가능
  구체적인 실패 조건과 처리 방식, 사용자의 선택 이유를 확인했다.
  검증 범위는 테스트 내용과 기록 확인이며 실제 운영 성과는 별도 확인이 필요하다.

### 문제와 구현

- 외부 게시가 성공했지만 작업자는 타임아웃을 받는 상황을 테스트가 재현한다.
  - 근거: tests/test_publisher.py:30, test_response_lost_after_publish
- 작업자는 요청 전에 중복 방지 키를 저장하고 재시작 후 같은 키를 읽는다.
  - 근거: src/publisher.py:40, publish_job
  - 근거: src/job_store.py:20, load_job
- 같은 키의 재요청에는 외부 API가 기존 결과를 반환하는 계약을 전제로 한다.
```
