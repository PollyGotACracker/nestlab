## 착수 절차

### 1. 요청 확인

1. 사용자 요청에서 해결할 문제, 요청한 결과물, 대상과 범위, 명시한 조건을 추출한다.
2. 사용자가 직접 정한 내용, 추가한 해석, 확인이 필요한 사항을 구분한다.
   확정 전 문제 정의와 범위 초안은 작업 경과에 기록한다.
3. 문서 작업은 독자와 용도를, 자료와 값에 관한 요청은 필요한 대상과 범위를 확인한다.
4. 사용자가 정한 완료 기준을 확인하여 반영한다. 별도 기준이 없으면 사용자가 명시한 요구사항을 기준으로 둔다.

#### 1.1. 작업 문서 확인

1. 작업 문서 역할을 하는 폴더에서 현재 요청의 대상 파일, 기능명과 문제 증상을 찾는다.
2. 일치한 작업의 경과와 명세를 읽고, 현재 요청과 관련된 작업 상태, 확정 사항과 남은 작업을 확인한다.
3. 현재 상태와 남은 작업, 연결된 하위 문서를 전부 확인한다.
4. 기존 기록의 사실과 판단, 사용자 확정 사항과 현재 요청을 대조하여 보고한다.

#### 1.2. 위키 저장소 확인

1. 연결 가능한 위키 저장소가 있는지 파악한다.
2. 저장소에 명시된 검색 절차에 따라 현재 요청을 검색한다.
3. 확인한 근거가 현재 요청의 목표, 적용 조건과 버전에 맞으면 재사용한다.
4. 현재 요청과 달라진 내용, 부족한 근거와 충돌을 탐색 대상으로 정한다.
5. 추가로 확인할 항목마다 현재 요청과의 관련성과 조사 사유를 보고한다.

### 2. 상황 보고

1. 초기 이해에 대한 합의된 수정 의견은 기존 기록 확인과 탐색에 반영한다.
2. 요청을 어떻게 이해했는지 중간 보고하여 요청 해석을 사용자가 확인할 수 있게 한다.

### 3. 탐색

1. 요청 대상과 확인할 질문에 맞춰 조사 절차를 적용한다.
   - 저장소 파일과 실행 환경 확인은 `3.1. 저장소 조사`를 따른다.
   - 지침과 스킬의 생성 또는 변경은 `3.2. 지침과 스킬 조사`를 따른다.
   - 외부 사실 확인은 `3.3. 웹 조사`를 따른다.
2. 확인 범위를 정리한다.
   - 읽은 파일과 행 범위, 검색어, 제외한 경로를 기록한다.
   - 확인한 사실과 추론, 미확인 사항을 출처와 함께 구분한다.
   - 변경 대상과 관련 파일이 있으면 기존 흐름을 코드 블록으로 정리한다.
   - 기존 흐름에는 진입점, 호출하는 코드와 호출받는 코드, 같은 데이터를 읽는 검사를 포함한다.
   - 기존 흐름의 각 줄에 확인한 파일과 행을 붙인다.

#### 3.1. 저장소 조사

저장소 파일과 실행 환경을 확인할 때 적용한다.

##### 3.1.1. 목적과 설계 구조

1. README, 저장소 지침, 운영 문서를 우선 읽고 작업의 근거로 둔다.
   만약 사용자의 요청과 충돌하는 경우 즉시 보고하여야 한다.
2. 폴더 구조와 빌드 및 설치 설정 파일로 구성 요소와 진입점을 찾는다.
3. 요청 대상이 속한 구성 요소와 연결된 요소를 확인하여 영향을 받는 파일을 전부 조사한다.

##### 3.1.2. 실행 환경

1. 세션 실행 위치와 적용 에이전트를 확인한다.
2. 설치된 지침, 에이전트와 스킬을 연결 도구의 확인 결과 및 링크 대상으로 대조한다.
3. 다른 실행 기록은 당시 실행 위치에서 열 수 있었던 경로와 주입된 지침으로 판정한다.

##### 3.1.3. 요청 대상 탐색

1. 관련 구성 요소 안에서 대상 파일과 동작 및 인터페이스 확인에 필요한 파일을 연다.
2. 큰 파일은 검색어, 기호와 행 범위로 나눠 읽고 잘리거나 빠진 부분을 추가로 읽는다.
3. 결론이 의존하는 정의와 연결 절차, 호출하는 코드와 호출받는 코드를 함께 읽는다.
4. hook과 설정의 도구 입력은 각 runner의 실제 도구 정의 및 스키마와 대조한다.
5. 진입점부터 관련 동작을 끝까지 따라가 데이터 흐름을 확인한다.
6. 같은 기능의 구현이 여럿이면 현행, 이전 구현과 생성물을 근거와 함께 구분한다.
7. 이동 대상의 활성 참조와 링크를 확인하고, 연결 갱신 및 복구 방법을 조사한다.

##### 3.1.4. 기존 형식

1. 같은 종류 파일의 형식, 용어와 컨벤션을 확인한다.
2. 기존 컨벤션과 적용 원칙이 충돌하면 충돌 내용과 영향을 보고한다.
3. 지침은 적용 조건, 행동과 판정 기준이 겹치는 규칙을 검색한다.
4. 새 문서를 제안하기 전에 같은 작업을 다루는 기존 지침과 스킬을 검색한다.

##### 3.1.5. 출처와 이력

1. 설정과 권한 항목을 저장소 원본, 설치 도구 생성분과 사용자 항목으로 구분한다.
2. 사용자 항목으로 확인한 설정과 권한은 승인된 변경 범위에 따라 처리한다.
3. 변경 이력과 설치 도구의 병합 규칙으로 항목의 출처를 확인한다.
4. 설치본과 원본의 차이, 원본 사이의 정책 차이를 구분해 기록한다.
5. 과거 상태는 해당 시점의 원본과 변경 기록으로 대조한다.
6. 결함과 부재를 판정하기 전에 대상의 처리 규정과 실행 환경을 확인한다.
7. 로컬 상태는 실제 파일과 커맨드 결과로 확인한다.

##### 3.1.6. 영향 범위

- 영향받는 기능, 채널, 설정, 문서와 테스트
- 기존 동작과의 충돌
- 요구사항과 충돌하는 지침, 스킬, 코드와 설정
- 승인 및 보안 경계
- 명칭 충돌
- 같은 대상 파일을 다루는 다른 작업의 확정 사항과 작성 기준

##### 3.1.7. 로그와 재현 자료

1. 보안 문제가 없으면서 현재 환경에서 실행 가능한 로그 수집 커맨드는 직접 실행한다.
2. 사용자 환경에서만 실행할 수 있는 커맨드는 실행되는 내용, 필요한 이유를 설명해 제시한다.

##### 3.1.8. 문서 갱신 대상

1. 영향받는 운영 문서와 README를 본문 검색어로 검색한다.
2. 일치한 문서는 frontmatter `description`이 정한 범위의 내용이 바뀔 때만 갱신 대상으로 둔다.
   범위 밖 변경은 해당 코드의 주석과 docstring에 기록한다.
3. 갱신 대상의 위치와 검색어를 기록하고, 일치가 없으면 사용한 검색어를 기록한다.

#### 3.2. 지침과 스킬 조사

지침 문서(AGENTS.md, CLAUDE.md)나 스킬 문서(SKILL.md)의 생성 또는 변경이 요구될 때 적용한다.

##### 3.2.1. 현황 파악

1. 지침, 스킬 문서를 전수조사하여 확인하고 신설, 개정, 통합 중 필요한 처리를 정한다.
2. 기존 원문과 미커밋 변경을 확인하고 변경 대상과 보존할 내용을 정한다.
3. 기존 원문의 단순 정리, 또는 프로젝트 고유 설계 기반 수정의 경우 바로 `3.2.3. 내부 근거 확인`으로 진행한다.

##### 3.2.2. 외부 근거 확인

1. 생성과 수정 모두 작성 전 아래 대상에 `3.3. 웹 조사`를 적용한다.
2. 지침은 해결하려는 문제, 적용 상황, 목표를 검색어로 두고 관련 웹 문서를 확인한다.
   확인한 문제의 조건과 대응 근거를 작성할 문장에 연결한다.
3. 스킬은 그 스킬이 만들거나 수정할 결과물의 종류와 용도를 검색어로 두고 실제 공개 결과물을 찾아 원문을 확인한다.
   - 실제 결과물의 구성과 내용을 확인하고 수행 절차와 완료 기준에 연결한다.
   - 스킬 작성법 문서는 보조 근거로 사용하며 실제 결과물 확인은 별도로 수행한다.
     e.g. README 작성 스킬은 실제 공개 저장소의 README를, 포트폴리오 글 작성 스킬은 실제 게시글을 확인한다.

##### 3.2.3. 내부 근거 확인

1. 대상의 설계 근거 문서를 확인한다.
   - 참조 가능한 지식 저장소가 있는 경우 저장소를 검색해 근거 문서를 탐색한다.
   - 위키 검색 절차가 정해진 경우 해당 절차를 적용한다.
2. 찾은 근거 문서의 원문을 확인하고 관련 항목과 변경 근거를 연결한다.
3. 제안하는 문장은 적용 대상 범위를 사용자 작업 전체와 대조한다.
4. 제안 응답의 첫머리에 기존 문장 검색어와 일치한 `파일:행` 또는 일치 없음을 적는다.

#### 3.3. 웹 조사

외부 사실을 확인할 때 적용한다.

##### 3.3.1. 검색 계획

1. 외부 사실이 필요한 조사의 검색어는 요청의 문제, 적용 상황과 목표로 정한다.
   최초 검색어는 사용자가 언급한 대상, 상황과 목표로 작성하고 검색 전에 제시한다.
2. 확인할 내용에 맞춰 자료 유형을 선택한다.
   - 기능과 명세: 공식 문서와 변경 기록
   - 사용 관행: 공개 구현과 운영 사례
   - 사용 빈도: 통계와 사용량 자료
   - 문제 원인: 이슈와 수정 기록

##### 3.3.2. 원문 확인

1. 대상과 버전에 맞는 원문을 읽고 적용 조건과 갱신 시점을 확인한다.
   별도 버전 조건이 없으면 최신 자료를 우선 확인한다.
2. 특정 사실을 확인하면 반대 자료도 조사하고, 상충하는 원문의 근거와 적용 조건을 대조한다.
3. 다른 명칭의 자료는 원문에서 요청 대상과의 관계를 확인한다.
4. 후속 검색어는 요청 대상과 질문을 유지하며 원문에서 확인한 용어로 확장한다.
5. 결과가 모호하거나 근거가 부족하면 검색어와 자료 범위를 바꿔 추가 조사한다.
6. 공식 원문에 명시된 옵션 이름, 기본값과 지원 여부는 원문으로 확인한다.
7. 도구, 라이브러리와 서비스의 추천 후보는 다음 지표의 확인값과 출처를 함께 정리한다.
   - 채택 규모
   - 커뮤니티 활동
   - 마지막 갱신
   - 이슈 종료 빈도
   - deprecated 여부

##### 3.3.3. 근거 정리

1. 확인한 사실에 원문 링크를 붙이고 열람 범위를 기록한다.
2. 자료가 부족하면 검색 범위와 부족한 항목을 밝히고 사용자 요구와 확인한 근거를 구분한다.
   확인하지 못한 지표는 미확인으로 구분한다.
3. 확인한 사실과 추론, 미확인 사항은 `3. 탐색` 절의 확인 범위 정리에 반영한다.

### 4. 조사 결과 보고와 논의

1. 도구, 라이브러리와 서비스의 추천 후보는 필요한 기능, 호환성과 제약이 확인된 것으로 정한다.
   - 해결 후보의 적용 조건과 한계는 저장소 조건과 대조한다.
   - 후보 비교가 필요한 단계에서는 대안과 추천하기 어려운 조건도 조사한다.
2. 사용자 요청과 탐색 사실을 대조해 문제 정의와 범위 초안을 작성한다.
3. 다음 내용을 구분해 응답으로 보고한다.
   - 사용자 요청 요약
   - 문제 정의 초안
   - 추가한 문제 정의와 근거
   - 조사로 확인한 사항
   - 조사 사실과 출처
   - 사용자 판단에 대한 반대 근거
   - 계획 보완점
   - 저장소 개선점
   - 조사로 판단한 사항
     - 현재 계획을 구현하고 실제로 실행했을 때 실패를 만들 수 있는 지점의 수정 내용
     - 기능 추가 시 현재 모듈에 추가할지, 새로운 모듈을 만들어 추가할지 판단한 내용
     - 최적 대안 후보들의 장점, 단점, 알려진 이슈와 한계와 위험을 사실에 기반하여 분석한 내용
       요구사항 미충족 등 제외 대안 목록은 간단하게 요약 보고한다.
4. 합의 전 사용자 메시지는 역할 구분 없이 주장으로 받아 근거를 조사하고, 조사 근거를 바탕으로 합의된 결론이 나올 때까지 사용자와 논의한다.
   합의할 때마다 같은 번호로 문제 정의를 재확정한다.
5. 논의 과정에서 요구사항이 추가되거나 변경되면 해당 사항을 `1. 요청 확인`부터 다시 수행한다.
6. 논의가 결론에 도달하지 못하면 탐색을 재수행한 뒤, 조사 결과를 보고하고 논의를 이어간다.
7. 논의 결과에 따라 문제 정의와 범위 초안을 수정, 추가하거나 구체화한다.
8. 사용자가 정한 완료 기준을 유지하고 추가하거나 변경하려는 완료 기준은 제안을 통해 사용자 확인을 받는다.
9. 미측정 범위와 확인 가능한 대안을 보고한다. 측정 방법이 없는 기준도 유지한다.
10. 문제와 범위의 판단에 영향을 주는 잠재 위험과 한계를 확정 전에 보고한다.
11. 확정된 문제나 범위를 바꾸려면 근거와 영향을 보고하고 사용자 확인 뒤 반영한다.

### 5. 추가 조사 항목 작성

1. 탐색으로 확인한 사실과 조사에서 확인할 원인 및 해결 후보를 구분한다.
2. 추가 조사 필요 판단 기준의 예시는 다음과 같다. 필요하다면 추가 기준을 두고 그 근거를 제시한다.  
   조사가 끝나면 모든 모호한 항목에 대한 원인이 조사되고 저장소에서 실제로 구현할 구체적 방법이 반환되어야 한다.
   - 복잡한 설계가 요구되거나 중요도가 높은 작업에서 비교 조사가 필요한 경우
   - 요구사항을 완전히 충족하는 대안이 없어 절충 또는 타협이 필요한 경우
   - 저장소의 특정 설계에 적합한 대안을 찾는 경우
   - 구현을 위해 필요한 API가 특정 기술에서 제공하지 않아 대안을 찾는 경우
   - 특정 기술에서 해결되지 않은 이슈에 대응해야 하는 경우
   - 외부 위험을 찾았으나 해결 수단이 모호하여 추가 조사가 필요한 경우
3. 확정한 문제마다 이미 근거가 있는 내용과 추가 조사가 필요한 내용을 구분한다.
4. 조사로 발견한 후보를 비교할 판단 기준은 사용자 요구사항 충족을 우선으로 둔다.
   수치 임계값은 사용자가 정한 경우에 적용한다.
5. 추가 조사 항목마다 연결된 문제와 조사 목적, 확인할 근거를 적는다.

### 6. 검증 및 모델 호출 실측 항목 작성

1. 검증과 모델 호출 실측이 필요한 기준은 대상과 환경, 방법 및 관측할 결과를 정한다.
2. 대체 수단을 사용하면 원래 대상과의 차이 및 입증할 수 있는 범위를 설명한다.
3. 시험, 스크립트와 브라우저 MCP처럼 비용이 없는 실행은 실행 확인으로 정하고 승인 없이 실행한다.
4. 조사 계획에 영향을 주는 잠재 위험과 한계를 정리한다.

### 7. 보고

1. 문제 정의와 범위를 `question-kickoff` 양식의 확정 질문으로 확인한다. 폐기는 폐기 질문으로 확인한다.
   Codex에서는 `request_user_input`으로 묻는다. 문제 정의 절은 hook이 답에 따라 기록한다.
   생성된 작업 상태 `미개시`와 승인 상태 `승인 대기` 및 hook 관리 필드의 초기값을 보존한다.
2. hook이 기록한 문제 정의 절을 읽어 확인한다. 문제 정의는 확인 질문으로만 바꾼다.
   기록이 없으면 질문 형식을 고쳐 다시 묻고 조사 승인 요청을 이어간다.
3. 생성기의 `--print-template approval-research` 출력 양식의 제목과 필드로 조사 승인 요청을 작성한다.
4. 권한은 기존 단계와 확정 답 판정으로 결정한다.
5. 같은 사용자 턴의 Stop 재작성은 안내한 제목과 모든 필드를 포함한 해당 절 전체로 보완한다.
   최초 요청과 보완을 결합한 조사 승인 요청의 검사를 통과하고 새 전체 요청은 이전 요청을 대체한다.
6. 조사 승인 뒤 첫 줄이 `[research]`뿐인 메시지를 받으면 조사 단계 절차를 시작한다.
