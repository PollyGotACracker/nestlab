## 계획 규칙

- 문제 정의, 조사, 반증, 후보 비교와 명세 작성을 하나의 plan 단계에서 처리한다.
  계획은 구현 승인 요청 하나로 계획과 구현 범위를 함께 확정한다.
- 응답과 질문은 아래 양식을 생성기의 `--print-template <양식>` 출력으로 확인해 작성한다.
  - 계획 보고: `info-plan`
  - 조사 승인 요청: `approval-research`
  - 검토 표시: `info-review`
  - 합의한 확정안 표시: `info-confirmed`
  - 요구사항 확정 질문과 후보 확정 질문: `question-confirmed`
  - 구현 승인 요청: 양식 대신 `구현 승인 요청: <작업-id>` 한 줄을 쓰고 hook이 `approval-implement` 생성 출력을 표시한다.
- 한계에는 설계 자체의 제약을, 위험에는 외부 이슈의 조건과 영향을 쓰고 `출처:`를 붙인다.
  실행 결과가 필요한 기준은 사후 실측 계획(대상, 방법, 관측할 결과)으로 쓴다.

## 계획 절차

### 1. 요청 확인

1. 사용자 요청에서 해결할 문제, 요청한 결과물, 대상과 범위, 명시한 조건을 추출한다.
2. 사용자가 직접 정한 내용, 추가한 해석, 사용자에게 물을 사항을 구분한다.
   확정 전 문제 정의와 범위 초안은 작업 경과에 기록한다.
3. 문서 작업은 독자와 용도를, 자료와 값에 관한 요청은 필요한 대상과 범위를 확인한다.
4. 사용자가 정한 완료 기준을 반영한다. 별도 기준이 없으면 명시한 요구사항을 기준으로 둔다.

#### 1.1. 작업 선택

1. 작업 색인(`.agent-logs/task/index.md`)의 현재 진행 작업 절에서 대상 작업을 확인한다.
2. 사용자가 다른 작업을 지정하거나 다른 작업을 진행하면 그 절의 줄을 해당 작업 줄로 바꾼다.
   줄 형식은 `- [<작업명>](<작업-id>/status.md), <작업 단계>`이고 다른 절은 hook이 갱신한다.
3. 선택한 작업의 경과와 명세를 읽고 확정 사항, 남은 작업과 연결된 하위 문서를 확인한다.
4. 기존 기록의 사실과 판단, 사용자 확정 사항과 현재 요청을 대조하여 보고한다.

#### 1.2. 위키 저장소 확인

1. 현재 세션 경로 안의 위키 자료를 저장소에 명시된 검색 절차로 검색한다.
2. 확인한 근거가 현재 요청의 목표, 적용 조건과 버전에 맞으면 재사용한다.
3. 현재 요청과 달라진 내용, 부족한 근거와 충돌을 사전 조사 대상으로 정한다.

### 2. 사전 조사

1. 요청 대상과 확인할 질문에 맞춰 하위 절차를 적용한다.
   - 저장소 파일과 실행 환경: `2.1. 저장소 조사`
   - 지침과 스킬의 생성 또는 변경: `2.2. 지침과 스킬 조사`
   - 외부 사실: `2.3. 웹 조사`
2. 변경 대상에 기존 파일이 있는 설계 작업은 계획 확인 전에 `2.3. 웹 조사`의 자료 유형별 원문과 반대 자료 본문을 직접 연다.
   열람한 URL과 확인한 동작을 명세의 근거로 기록한다.
3. 확인 범위를 정리한다.
   - 읽은 파일과 행 범위, 검색어, 제외한 경로를 기록한다.
   - 변경 대상과 관련 파일이 있으면 기존 흐름을 코드 블록으로 정리한다.
   - 기존 흐름에는 진입점, 호출하는 코드와 호출받는 코드, 같은 데이터를 읽는 검사를 포함한다.
   - 기존 흐름의 각 줄에 확인한 파일과 행을 붙인다.

#### 2.1. 저장소 조사

1. README, 저장소 지침, 운영 문서를 먼저 읽고 사용자 요청과 충돌하면 즉시 보고한다.
2. 폴더 구조와 빌드 및 설치 설정 파일로 구성 요소와 진입점을 찾는다.
3. 요청 대상과 연결된 구성 요소를 확인하여 영향을 받는 파일을 전부 조사한다.
4. 세션 실행 위치와 적용 에이전트, 설치된 지침과 스킬의 연결 상태를 연결 도구 결과로 대조한다.
5. 대상 파일은 정의와 연결 절차, 호출하는 코드와 호출받는 코드를 함께 읽는다.
   - 큰 파일은 검색어, 기호와 행 범위로 나눠 읽고 잘린 부분을 추가로 읽는다.
   - hook과 설정의 도구 입력은 각 runner의 실제 도구 정의 및 스키마와 대조한다.
   - 진입점부터 관련 동작을 끝까지 따라가 데이터 흐름을 확인한다.
   - 같은 기능의 구현이 여럿이면 현행, 이전 구현과 생성물을 근거와 함께 구분한다.
   - 이동 대상의 활성 참조와 링크, 연결 갱신 및 복구 방법을 조사한다.
6. 같은 종류 파일의 형식, 용어와 컨벤션을 확인하고 적용 원칙과의 충돌을 보고한다.
7. 설정과 권한 항목을 저장소 원본, 설치 도구 생성분과 사용자 항목으로 구분한다.
   과거 상태는 해당 시점의 원본과 변경 기록으로, 로컬 상태는 실제 파일과 커맨드 결과로 확인한다.
8. 영향 범위를 확인한다.
   - 영향받는 기능, 채널, 설정, 문서와 테스트
   - 기존 동작, 지침, 스킬, 코드와 설정의 충돌
   - 승인 및 보안 경계와 명칭 충돌
   - 같은 대상 파일을 다루는 다른 작업의 확정 사항과 작성 기준
9. 현재 환경에서 보안 문제 없이 실행할 수 있는 로그 수집 커맨드는 직접 실행한다.
   사용자 환경 전용 커맨드는 실행 내용과 필요한 이유를 함께 제시한다.
10. 영향받는 운영 문서와 README를 본문 검색어로 검색해 갱신 대상을 정한다.
    frontmatter `description` 범위 밖 변경은 해당 코드의 주석과 docstring에 기록한다.

#### 2.2. 지침과 스킬 조사

1. 지침과 스킬 문서를 전수조사해 신설, 개정, 통합 중 필요한 처리를 정한다.
2. 기존 원문과 미커밋 변경을 확인하고 변경 대상과 보존할 내용을 정한다.
3. 단순 정리나 프로젝트 고유 설계 기반 수정이 아니면 작성 전에 `2.3. 웹 조사`를 적용한다.
   - 지침: 해결할 문제, 적용 상황, 목표를 검색어로 두고 대응 근거를 작성할 문장에 연결한다.
   - 스킬: 결과물의 종류와 용도로 실제 공개 결과물을 찾아 절차와 완료 기준에 연결한다.
4. 설계 근거 문서는 참조 가능한 지식 저장소의 검색 절차로 찾아 원문을 확인한다.
5. 제안 응답의 첫머리에 기존 문장 검색어와 일치한 `파일:행` 또는 일치 없음을 적는다.

#### 2.3. 웹 조사

1. 최초 검색어는 사용자가 언급한 대상, 상황과 목표로 작성하고 검색 전에 제시한다.
2. 확인할 내용에 맞춰 자료 유형을 선택한다.
   - 기능과 명세: 공식 문서와 변경 기록
   - 사용 관행: 공개 구현과 운영 사례
   - 사용 빈도: 통계와 사용량 자료
   - 문제 원인: 이슈와 수정 기록
3. 대상과 버전에 맞는 원문 본문을 열어 적용 조건과 갱신 시점을 확인한다.
   별도 버전 조건이 없으면 최신 자료를 우선한다.
4. 반대 자료도 조사하고 상충하는 원문의 근거와 적용 조건을 대조한다.
5. 다른 명칭의 자료는 원문에서 요청 대상과의 관계를 확인한다.
6. 결과가 모호하면 원문에서 확인한 용어로 검색어와 자료 범위를 바꿔 추가 조사한다.
7. 도구, 라이브러리와 서비스 후보는 채택 규모, 커뮤니티 활동, 마지막 갱신,
   이슈 종료 빈도와 deprecated 여부의 확인값과 출처를 정리한다.
8. 확인한 사실에 원문 링크와 열람 범위를 붙인다.
   권한이나 보안 경계로 열 수 없는 자료만 그 조건과 영향을 기록한다.

### 3. 조사 담당 배정 판단

1. 사전 조사로 답이 정해지지 않은 질문을 아래 기준으로 나눈다.
   - 직접 처리: 몇 번의 도구 호출로 끝나는 확인, 공식 문서 1~2개로 답이 정해지는 질문,
     사용자와 의견을 주고받는 확인
   - 조사 담당 배정: 병렬로 나눌 수 있는 독립 조사, 복수 대안 비교,
     메인 맥락에 둘 필요 없는 대량 출력
2. 직접 처리 항목은 같은 턴에 조사하고 결과를 확인 범위에 반영한다.
3. 배정 항목은 조사 문서의 조사 계획에 질문, 판단 기준, 결론 형식으로 작성한다.
   조사 항목마다 연결된 문제와 이미 근거가 있는 내용을 구분한다.
   후보의 판단 기준은 사용자 요구사항 충족을 우선하고 수치 임계값은 사용자가 정한 값을 쓴다.
4. `approval-research` 양식으로 조사할 항목과 배정 사유를 사용자에게 확인받는다.
5. 승인된 조사 항목은 서로 독립된 항목끼리 나눠 조사 담당에 동시에 배정한다.
6. 조사 결과는 반증 담당의 반증을 거쳐 후보로 정리한다.
   근거가 빠진 항목과 구현안이 없는 항목은 직접 조사하거나 재배정한다.

### 4. 논의와 문제 정의

1. 사용자 요청과 조사 사실을 대조해 문제 정의와 범위 초안을 작성한다.
2. `info-plan` 양식으로 다음 내용을 구분해 보고한다.
   - 사용자 요청 요약과 문제 정의 초안, 추가한 문제 정의와 근거
   - 조사 사실과 출처, 사용자 판단에 대한 반대 근거
   - 계획 보완점과 저장소 개선점
   - 실행했을 때 실패할 수 있는 지점과 수정 내용
   - 기능 추가 위치(현재 모듈 또는 새 모듈)의 판단
   - 대안 후보의 장점, 단점, 알려진 이슈, 한계와 위험
3. 합의 전 사용자 메시지는 주장으로 받아 근거를 조사하고 합의된 결론까지 논의한다.
4. 문제와 해결안이 합의되면 `info-confirmed` 양식으로 확정안을 표시한다.
   그 뒤 직전 확정안 원문을 기준으로 `question-confirmed` 양식의 확정, 폐기 질문을 한다.
   Codex에서는 `request_user_input`으로 묻는다.
   확정 답 뒤 hook이 사용자 확인 시각과 확정안 응답 원문을 명세 요구사항 절에 기록한다.
   요구사항 절에서 작성할 칸은 검증과 Test Case이다.
5. 요구사항이 추가되거나 바뀌면 `1. 요청 확인`부터 다시 수행하고 같은 번호로 재확정한다.
   확정된 문제를 바꾸려면 근거와 영향을 보고하고 추가 합의, 교체, 폐기 질문으로 확인한다.
6. 논의가 결론에 도달하지 못하면 사전 조사를 다시 수행하고 결과를 보고한다.
7. 사용자가 정한 완료 기준을 유지하고, 추가하거나 바꿀 완료 기준은 제안해 확인받는다.
8. 문제와 범위의 판단에 영향을 주는 한계와 위험을 확정 전에 보고한다.

### 5. 사전 실측

1. 검증과 모델 호출 실측이 필요한 기준마다 대상과 환경, 방법 및 관측할 결과를 정한다.
2. 시험, 스크립트와 브라우저 MCP처럼 모델 호출 비용이 없는 실행은 승인 없이 직접 실행한다.
3. 계획 판단에 모델 호출 결과가 필요하면 `approval-measure` 양식으로 승인받아 실행한다.
4. 대체 수단을 쓰면 원래 대상과의 차이와 입증할 수 있는 범위를 설명한다.
5. 구현 뒤에만 관측할 수 있는 결과는 완료 기준의 사후 실측 줄에 대상과 방법을 적는다.

### 6. 구현 승인 요청

1. 조사와 반증 결과로 후보를 정리해 `info-review` 양식으로 표시하고 논의한다.
   합의 뒤 `info-confirmed` 확정안을 표시하고 `question-confirmed` 질문으로 확정한다.
2. 확정 답이 명세 요구사항 목록에 기록되었는지 읽어 확인한다.
3. 모든 확정 문제에 연결된 요구사항이 있는지 대조하고 검토할 안이 남지 않았는지 확인한다.
4. 확정안 기록을 확인하고 요구사항의 검증과 Test Case, 명세의 검증 계획을 완결한다.
   차단 동작을 바꾸는 요구사항은 정상 입력과 차단 입력 Test Case를 각각 한 개 이상 둔다.
5. 응답에 `구현 승인 요청: <작업-id>` 한 줄을 써서 구현 승인을 요청한다.
6. 같은 턴에 양식 응답을 다시 쓰면 양식 출력을 다시 확인하고 해당 절 전체를 다시 쓴다.
   새 전체 요청은 이전 요청을 대체한다.

## 출력 검사

- 대상: 응답
- 금지: `approval-plan|계획 승인 요청` 계획은 구현 승인 요청 줄로 확정한다.
- 금지: `근거 출처` 출처 표기는 출처: 형식으로 쓴다.
- 금지: `미측정 범위` 구현 뒤에 확인할 결과는 사후 실측 줄에 대상과 방법으로 쓴다.
- 금지: `(?:한계|위험):\s*(?:미확인|미검증|미완료|미측정)` 한계에는 설계 제약, 위험에는 외부 이슈의 조건과 영향을 쓴다.
